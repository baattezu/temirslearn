Принцип подстановки Барбары Лисков (1987) — самый «математический» из SOLID и самый часто непонятый. Формулировка: если S — подтип T, то объекты T в программе можно заменить объектами S, и **корректность программы не нарушится**.

Ключевое слово — *корректность*. Не «компилируется», а «ведёт себя так, как ожидает код, написанный для родителя».

## Квадрат — не прямоугольник

В геометрии квадрат — частный случай прямоугольника. Кажется естественным: `class Square extends Rectangle`. Попробуй прогнать тест, написанный для прямоугольника:

<LspTest />

Проблема не в геометрии, а в **поведении**. У изменяемого `Rectangle` есть неявное обещание: `setHeight` меняет только высоту. `Square` это обещание нарушает, и любой код, который полагался на него, ломается. «Является» в жизни ≠ «можно подставить» в программе.

Решения:
- сделать фигуры **неизменяемыми** — тогда `Square` и `Rectangle` просто разные значения, и конфликта нет;
- не наследовать: `Square` и `Rectangle` — два независимых `Shape`.

## Контракт: что наследник может и не может

Наследник обязан соблюдать **контракт** родителя:

| Наследник может | Наследник не может |
|---|---|
| принимать **больше** входов (ослабить предусловия) | требовать больше, чем родитель (усилить предусловия) |
| гарантировать **больше** (усилить постусловия) | гарантировать меньше (ослабить постусловия) |
| бросать подтипы объявленных исключений | бросать новые неожиданные исключения |
| — | нарушать инварианты родителя |

## Нарушения LSP в реальном коде

**`UnsupportedOperationException`** — самый частый признак.

```java
List<String> names = List.of("Ада", "Алан");
names.add("Грейс");   // UnsupportedOperationException
```

`List.of` возвращает неизменяемый `List`, хотя интерфейс `List` обещает `add`. Это осознанный компромисс в JDK (документирован как «optional operation»), но с точки зрения LSP — нарушение: код, принимающий `List`, не знает, можно ли его менять.

**Усиленное предусловие.**

```java
class Repository { void save(Entity e) { ... } }
class AuditedRepository extends Repository {
    @Override void save(Entity e) {
        if (e.createdBy() == null) throw new IllegalArgumentException();   // родитель такого не требовал
        super.save(e);
    }
}
```

Код, который работал с `Repository`, внезапно падает с `AuditedRepository`.

**Пустые реализации.** `class Penguin extends Bird` с `fly() {}`, который ничего не делает. Код «отправь всех птиц в полёт» молча не работает. Значит, иерархия неверна: способность летать — отдельный интерфейс `Flying`.

## Как проверять

LSP проверяется **тестами контракта**: один набор тестов, написанный для родителя или интерфейса, должен проходить на каждой реализации. Если для наследника приходится тест «отключить» — подстановка нарушена.

```java
abstract class StackContractTest {
    abstract Stack<Integer> create();
    @Test void popReturnsLastPushed() {
        var s = create();
        s.push(1); s.push(2);
        assertEquals(2, s.pop());
    }
}
class ArrayStackTest extends StackContractTest { Stack<Integer> create() { return new ArrayStack<>(); } }
class LinkedStackTest extends StackContractTest { Stack<Integer> create() { return new LinkedStack<>(); } }
```

<Takeaways>
- **LSP**: подтип можно подставить вместо родителя без нарушения **корректности** — не только компиляции.
- Квадрат и прямоугольник: «является» в жизни ≠ «подставляем» в коде. Виноваты изменяемые сеттеры; лечат неизменяемостью или отказом от наследования.
- Наследник может ослабить предусловия и усилить постусловия, но не наоборот, и не может нарушать инварианты.
- Признаки нарушения: `UnsupportedOperationException`, усиленные проверки, пустые реализации.
- Проверка — **тесты контракта**, общие для всех реализаций.
</Takeaways>
