SOLID — пять принципов проектирования классов, которые Роберт Мартин собрал в начале 2000-х (аббревиатуру придумал Майкл Фезерс). Их спрашивают почти на каждом собесе для бэкендера. Слабый ответ — расшифровать буквы. Сильный — объяснить, **какую боль лечит** каждый принцип и где он вредит, если довести до абсурда.

Все пять — про одно: **как менять код, не ломая остальное**.

## S — Single Responsibility: одна причина для изменения

Формулировка «класс должен делать одно дело» вводит в заблуждение — непонятно, что считать «одним делом». Мартин уточнял: у модуля должна быть **одна причина для изменения**, а точнее — он должен отвечать перед **одним актором** (одной группой людей, которые просят изменений).

Признаки нарушения SRP:
- класс меняют в разных задачах разных команд;
- в нём импорты из совсем разных миров: SQL, HTTP, PDF, бизнес-правила;
- его трудно назвать без «и» или без слова «Manager».

**Перегиб**: класс на каждую функцию. Если две вещи всегда меняются вместе — им место рядом.

## O — Open/Closed: открыт для расширения, закрыт для изменения

Бертран Мейер, 1988: модуль должен позволять **добавлять новое поведение, не меняя существующий код**. Зачем? Код, который работает и покрыт тестами, лучше не трогать: каждая правка — риск регрессии.

<Compare
  left={{ label: "Каждый новый тип — правка", code: `class DiscountService {
    BigDecimal discount(Customer c, BigDecimal sum) {
        switch (c.type()) {
            case REGULAR: return ZERO;
            case VIP:     return sum.multiply(new BigDecimal("0.1"));
            case STAFF:   return sum.multiply(new BigDecimal("0.3"));
            // новый тип клиента = правка здесь
            // и во всех похожих switch по проекту
        }
    }
}` }}
  right={{ label: "Новое — новым классом", code: `interface DiscountPolicy {
    boolean appliesTo(Customer c);
    BigDecimal discount(BigDecimal sum);
}

class DiscountService {
    private final List<DiscountPolicy> policies;   // Spring соберёт все бины
    BigDecimal discount(Customer c, BigDecimal sum) {
        return policies.stream()
            .filter(p -> p.appliesTo(c))
            .map(p -> p.discount(sum))
            .max(naturalOrder()).orElse(ZERO);
    }
}
// новая скидка = новый @Component, DiscountService не меняется` }}
/>

Механизмы OCP: полиморфизм и интерфейсы, стратегии, плагины, события, конфигурация.

**Перегиб**: делать точки расширения «на всякий случай» — интерфейс с одной реализацией, фабрика фабрик. Расширяемость нужна там, где изменения **реально случаются**. Правило трёх: первый раз пиши прямо, на третий похожий случай — выделяй абстракцию.

<Callout kind="info" title="OCP и sealed-типы">
OCP хорош, когда часто добавляются **новые варианты**. Если варианты стабильны, а часто добавляются **новые операции** над ними — удобнее sealed-иерархия и `switch` (см. «проблему выражения» в уроке о полиморфизме). Принцип — инструмент под конкретную ось изменений, а не закон.
</Callout>

<Takeaways>
- SOLID — про то, **как менять код, не ломая остальное**.
- **SRP**: одна **причина для изменения** (один актор), а не «один метод». Признаки нарушения — разные команды правят один класс, смешанные импорты, «Manager» в имени.
- **OCP**: новое поведение — новым кодом, а не правкой старого. Механизмы — полиморфизм, стратегии, плагины.
- Перегибы: класс на каждую функцию; абстракции «на всякий случай». Правило трёх.
</Takeaways>
