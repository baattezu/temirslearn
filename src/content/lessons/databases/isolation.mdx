Уровни изоляции — это договор о том, **какие аномалии** база разрешает при параллельной работе транзакций. На собесе важно не перечислить четыре уровня из стандарта, а знать, как они **реально** работают в Postgres и какую аномалию ловит каждое решение.

## Аномалии

| Аномалия | Что происходит |
|---|---|
| **Грязное чтение** | читаю незакоммиченные изменения соседа |
| **Неповторяющееся чтение** | читаю строку дважды — значения разные |
| **Фантом** | повторяю запрос с WHERE — появились новые строки |
| **Потерянное обновление** | два read-modify-write, один перезаписывает другого |
| **Write skew** | две транзакции читают общее условие и меняют **разные** строки, нарушая инвариант |

## Уровни в Postgres

| Уровень | Грязное | Неповторяющееся | Фантом | Lost update | Write skew |
|---|---|---|---|---|---|
| READ UNCOMMITTED | нет* | да | да | да | да |
| **READ COMMITTED** (default) | нет | да | да | да | да |
| **REPEATABLE READ** | нет | нет | нет** | нет (ошибка) | да |
| **SERIALIZABLE** | нет | нет | нет | нет | нет (ошибка) |

\* В Postgres READ UNCOMMITTED ведёт себя как READ COMMITTED: грязного чтения нет вообще, MVCC его не допускает.
\** По стандарту фантомы на RR разрешены, но в Postgres RR — это **snapshot isolation**, и фантомов не будет.

Главное слово в таблице — **«ошибка»**. Postgres на высоких уровнях не ждёт и не сериализует транзакции в очередь. Он даёт им работать параллельно, а потом **откатывает** ту, что нарушила бы гарантию. Приложение обязано уметь **повторять** транзакцию при `SQLSTATE 40001`.

## Попробуй три аномалии

### Потерянное обновление

Классика ORM: прочитать объект, поменять поле в коде, сохранить. В READ COMMITTED второй UPDATE просто перезапишет первый. Варианты защиты:

1. **Атомарный UPDATE**: `SET likes = likes + 1` вместо вычисления в приложении. Работает даже в RC — сценарий «Два UPDATE одной строки».
2. **Пессимистичная блокировка**: `SELECT … FOR UPDATE` при чтении. Вторая транзакция ждёт на SELECT.
3. **Оптимистичная**: колонка `version` и `UPDATE … WHERE id = ? AND version = ?`. Если обновилось 0 строк — кто-то успел раньше, повторяем. Так делает `@Version` в JPA.
4. **REPEATABLE READ** + повтор при ошибке сериализации.

### Write skew

Самая коварная аномалия: каждая транзакция по отдельности проверяет инвариант («дежурных ≥ 1»), но они меняют **разные** строки. Блокировок строк не возникает, и REPEATABLE READ её **не ловит**.

Ловят её так:

- **SERIALIZABLE**: Postgres использует SSI (Serializable Snapshot Isolation) — отслеживает, кто что читал (predicate locks), и откатывает транзакцию, если появляется опасный цикл зависимостей «прочитал то, что ты потом изменил» в обе стороны;
- `SELECT … FOR UPDATE` по **всем** строкам условия — материализовать конфликт;
- ограничение на уровне схемы, если инвариант это позволяет (`UNIQUE`, `EXCLUDE`, триггер с блокировкой).

<Callout kind="tip" title="На собесе: какой уровень выбрать">
Хороший ответ: «По умолчанию READ COMMITTED плюс атомарные UPDATE, `FOR UPDATE` или оптимистичная версия там, где нужен read-modify-write. SERIALIZABLE — там, где инвариант охватывает много строк, и только вместе с логикой повтора транзакции. REPEATABLE READ — для консистентных отчётов и выгрузок, которые должны видеть один снимок».
</Callout>

## Повтор транзакции — обязательная часть

Ошибки `40001 serialization_failure` и `40P01 deadlock_detected` — это не баги, а нормальный режим работы. Повторять надо **всю** транзакцию с начала, включая чтения, иначе решение будет принято на старых данных.

```java
for (int attempt = 1; ; attempt++) {
    try {
        return tx.execute(() -> transfer(from, to, amount)); // BEGIN … COMMIT
    } catch (CannotSerializeTransactionException | DeadlockLoserDataAccessException e) {
        if (attempt == 5) throw e;
        Thread.sleep(ThreadLocalRandom.current().nextInt(10, 50) * attempt);
    }
}
```

<Takeaways>
- Postgres: **RC** (default), **RR** = snapshot isolation, **SERIALIZABLE** = SSI. Грязного чтения нет нигде.
- RC: неповторяющееся чтение и **потерянное обновление** при read-modify-write в приложении.
- RR: снимок на транзакцию; при конфликте записи — **ошибка**, а не ожидание. **Write skew** проходит.
- SERIALIZABLE ловит write skew, откатывая одну транзакцию (`40001`).
- Lost update лечится атомарным UPDATE, `FOR UPDATE`, оптимистичной версией или RR + повтор.
- Высокие уровни требуют **повтора всей транзакции** при `40001`/`40P01`.
</Takeaways>
