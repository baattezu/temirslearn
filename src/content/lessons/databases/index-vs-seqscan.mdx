Индекс не всегда быстрее. Планировщик PostgreSQL для каждого запроса оценивает **стоимость** нескольких планов и берёт самый дешёвый. Если понимать, из чего складывается эта стоимость, становится ясно, почему «индекс есть, а Postgres его не использует», и это уже уровень разговора senior-бэкендера.

## Единицы стоимости

Стоимость — это не миллисекунды, а условные единицы. За единицу взято последовательное чтение одной 8-КБ страницы:

| Параметр | По умолчанию | Что означает |
|---|---|---|
| `seq_page_cost` | 1.0 | прочитать страницу подряд |
| `random_page_cost` | 4.0 | прочитать страницу в случайном месте |
| `cpu_tuple_cost` | 0.01 | обработать строку |
| `cpu_index_tuple_cost` | 0.005 | обработать запись индекса |
| `cpu_operator_cost` | 0.0025 | вычислить оператор, например `=` в WHERE |

Дефолт `random_page_cost = 4` придуман для вращающихся дисков. На SSD случайное чтение почти такое же дешёвое, поэтому там обычно ставят 1.1–1.5, и планировщик начинает охотнее выбирать индекс.

## Три плана

- **Seq Scan** читает все страницы таблицы по порядку: `страницы × 1.0 + строки × (0.01 + 0.0025)`. Стоимость почти не зависит от того, сколько строк подходит.
- **Index Scan** спускается по B-tree и для каждой найденной строки идёт в кучу (heap). Если порядок в индексе не совпадает с физическим порядком строк, **каждая строка — случайное чтение**: `N × random_page_cost`. На малой выборке это дёшево, на большой — катастрофа.
- **Bitmap Heap Scan** — компромисс. Сначала по индексу собирается битовая карта нужных страниц, потом они читаются **один раз и по порядку**. Стоимость страницы плавно меняется от `random_page_cost` до `seq_page_cost` по мере того, как читается всё большая доля таблицы.

Обрати внимание, как точка перелома сдвигается:

- **SSD (1.1)** — индекс выгоден на куда большей доле строк;
- **широкие строки** — меньше строк на странице, Seq Scan дороже, индекс выигрывает дольше;
- **маленькая таблица** — Seq Scan выигрывает почти всегда: пара страниц читается быстрее, чем спуск по дереву.

<Callout kind="warn" title="Откуда планировщик знает селективность">
Из статистики: `ANALYZE` собирает гистограммы и самые частые значения по колонкам (`pg_stats`). Если статистика устарела или колонки коррелируют (город и страна), оценка числа строк ошибается в разы, и выбирается не тот план. Первое, что смотришь в `EXPLAIN ANALYZE`, — **rows оценённые против rows фактических**.
</Callout>

## Как это читать в EXPLAIN

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM documents WHERE tenant_id = 42 AND created_at > now() - interval '7 days';
```

- `cost=0.43..812.10` — стоимость запуска и полная стоимость в тех же единицах;
- `rows=1200` против `actual ... rows=58000` — ошибка оценки в 50 раз, ищи причину здесь;
- `Buffers: shared hit=... read=...` — hit пришли из кэша, read — с диска. Холодный и горячий запуск могут отличаться на порядок.

<Callout kind="tip" title="Твоя история">
Ты чинил регрессию полнотекстового поиска на индексе из 555K документов: 6.6 с → 50–70 мс. На собесе рассказывай её так: что показал `EXPLAIN ANALYZE`, где разошлись оценка и факт, какой план стал выбираться после исправления и почему. Модель стоимости из этого урока — словарь для такого рассказа.
</Callout>

<Takeaways>
- Планировщик выбирает план по **стоимости**: страницы × `seq/random_page_cost` + строки × CPU-константы.
- **Index Scan** — случайное чтение на каждую строку, хорош при малой селективности. **Bitmap** — читает нужные страницы один раз по порядку. **Seq Scan** — когда подходит заметная доля таблицы.
- `random_page_cost = 4` — дефолт для HDD. На SSD — 1.1–1.5.
- Плохой план чаще всего — это **плохая оценка строк**: устаревшая статистика или коррелирующие колонки. Лечится `ANALYZE` и расширенной статистикой (`CREATE STATISTICS`).
</Takeaways>
