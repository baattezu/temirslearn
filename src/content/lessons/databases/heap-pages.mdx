Таблица в PostgreSQL — это файл на диске, нарезанный на **страницы по 8 КБ**. Всё остальное — индексы, MVCC, VACUUM, bloat, HOT — становится понятным, когда видишь, как строки разложены внутри одной страницы.

## Файл → страницы → кортежи

У каждой таблицы есть файл `base/<oid базы>/<relfilenode>`. Его можно найти через `SELECT pg_relation_filepath('users')`. Файл режется на сегменты по 1 ГБ, а сегменты — на блоки (страницы) по 8192 байта. Postgres читает и пишет **только целыми страницами**: даже чтобы достать одно поле одной строки, в память поднимается вся страница.

Адрес строки называется **ctid** — `(номер страницы, номер line pointer)`. Его можно увидеть прямо в запросе: `SELECT ctid, * FROM users`. Именно ctid лежит в каждой записи индекса: индекс говорит «ищи на странице 0, слот 3».

## Раскладка страницы

Страница заполняется **с двух сторон навстречу друг другу**:

1. **Заголовок, 24 байта** (`PageHeaderData`). В нём LSN последней WAL-записи, контрольная сумма и два главных указателя: `pd_lower` и `pd_upper`.
2. **Массив line pointer'ов** (`ItemIdData`, по 4 байта). Он растёт от начала страницы вниз. Каждый указатель хранит смещение кортежа, его длину и состояние: `NORMAL`, `REDIRECT`, `DEAD` или `UNUSED`.
3. **Свободное место** между `pd_lower` (конец массива указателей) и `pd_upper` (начало самого нижнего кортежа).
4. **Кортежи**. Они растут с конца страницы вверх.

### Зачем line pointer, если можно хранить смещение прямо в индексе

Это слой косвенности. Индекс указывает на **слот**, а не на байты. Поэтому кортеж можно передвинуть внутри страницы, например при уплотнении после VACUUM: меняется только `lp_off` в слоте, а ctid и все индексы остаются верными. Посмотри на виджет: после VACUUM живые кортежи «съезжают» к концу страницы, а их ctid в таблице справа не меняются.

## Заголовок кортежа: 23 байта на каждую строку

| Поле | Байт | Что хранит |
|---|---|---|
| `t_xmin` | 4 | id транзакции, которая создала эту версию |
| `t_xmax` | 4 | id транзакции, которая удалила или обновила версию (0 — жива) |
| `t_cid` | 4 | номер команды внутри транзакции |
| `t_ctid` | 6 | ctid этой версии или **следующей** после UPDATE |
| `t_infomask2` | 2 | число атрибутов + флаги HOT |
| `t_infomask` | 2 | флаги: есть ли NULL, закоммичен ли xmin/xmax (hint bits) |
| `t_hoff` | 1 | смещение до данных |

23 байта выравниваются до 24, а если в строке есть NULL, добавляется ещё битовая карта NULL'ов. Итог: **каждая строка платит ~24 байта** заголовка плюс 4 байта line pointer'а. Таблица из одной колонки `integer` весит ~36 байт на строку (24 + 4 = 28, выровнено до 32, плюс 4 на указатель), а не 4. Отсюда ответ на вопрос «почему таблица из 100 млн int'ов занимает 3.5 ГБ».

## UPDATE не меняет строку на месте

Это главное, что надо вынести из урока. **UPDATE = INSERT новой версии + пометка старой.** Старой версии ставится `xmax = мой xid`, её `t_ctid` начинает указывать на новую. Старая остаётся на странице, потому что параллельные транзакции со старым снимком всё ещё могут её видеть. Это и есть MVCC. Видимость разберём в уроке про MVCC, а здесь важна физика:

- каждая обновлённая или удалённая строка оставляет **мёртвую версию**, которая занимает место, пока её не уберёт VACUUM;
- таблица с частыми UPDATE без VACUUM **пухнет** (bloat), даже если число строк не меняется.

### HOT: обновление без касания индексов

При обычном UPDATE новая версия получает новый ctid, значит, **в каждый индекс таблицы** надо вставить новую запись, даже если индексированные колонки не менялись. На таблице с пятью индексами один UPDATE — это шесть записей.

**HOT (Heap-Only Tuple)** экономит их. Если:

- не изменилась **ни одна индексированная колонка**,
- новая версия **помещается на ту же страницу**,

то в индексы ничего не пишется. Старая версия помечается `HOT_UPDATED`, новая — `HEAP_ONLY_TUPLE`, и индекс продолжает указывать на старый слот, откуда Postgres идёт по цепочке `t_ctid`. Когда VACUUM удаляет мёртвую голову цепочки, её слот превращается в **REDIRECT** на живую версию.

В виджете включи «Индекс по name» и сделай UPDATE: HOT пропадёт. Выключи — снова HOT.

<Callout kind="tip" title="На собесе">
«Почему не стоит индексировать колонку, которую часто обновляют?» Каждый UPDATE этой колонки ломает HOT и пишет во **все** индексы. Помогает и `fillfactor`: `ALTER TABLE t SET (fillfactor = 80)` оставляет 20% страницы пустыми, чтобы новым версиям было куда лечь, и HOT срабатывает чаще. Проверить долю HOT: `n_tup_hot_upd / n_tup_upd` в `pg_stat_user_tables`.
</Callout>

## VACUUM против VACUUM FULL

**VACUUM** работает внутри страницы:

- освобождает мёртвые версии, которые не видит ни один снимок;
- удаляет на них ссылки из индексов, и слоты становятся `UNUSED`;
- уплотняет страницу и отмечает свободное место в FSM (карте свободного места).

Файл таблицы при этом обычно **не уменьшается**. Место переиспользуется новыми строками. Блокировки берутся мягкие, чтение и запись идут параллельно.

**VACUUM FULL** переписывает таблицу в новый файл, кладя только живые строки. Файл сжимается, но **ctid меняются** (нажми VACUUM FULL в виджете и посмотри лог), поэтому все индексы строятся заново. На время работы таблица под `ACCESS EXCLUSIVE` — ни чтения, ни записи. В проде вместо него используют `pg_repack`.

## Порядок колонок тоже стоит места

Внутри кортежа каждое значение выравнивается по своему типу: `bigint` и `timestamptz` — по 8 байт, `integer` — по 4, `smallint` — по 2. Если после `boolean` идёт `bigint`, между ними вставляется 7 пустых байт. Переставь колонки или нажми «Уложить»:

Правило простое: **сначала 8-байтные, потом 4, 2, 1 и колонки переменной длины**. На больших таблицах это 10–20% места бесплатно. Но делать это можно только при создании таблицы — `ALTER TABLE` колонки не переставляет.

## TOAST: когда строка не влезает

Строка не может пересекать границу страницы. Если кортеж больше ~2 КБ (`TOAST_TUPLE_THRESHOLD`), Postgres сначала сжимает длинные значения, а если не помогло — выносит их в отдельную TOAST-таблицу кусками по ~2 КБ. В основной строке остаётся 18-байтный указатель. Отсюда два следствия: `SELECT *` по широким строкам дорогой (надо «склеить» TOAST), а `SELECT id, name` из той же таблицы — дешёвый.

<Takeaways>
- Таблица — файл из **страниц по 8 КБ**; Postgres читает и пишет только целыми страницами.
- Страница: заголовок 24 Б → **line pointers** растут вниз → свободное место → **кортежи** растут вверх.
- **ctid = (страница, слот)**; индекс ссылается на слот, поэтому кортеж можно двигать внутри страницы.
- Каждая строка платит **~24 Б заголовка** (xmin, xmax, ctid…) + 4 Б указателя.
- **UPDATE = новая версия**; старая остаётся мёртвой до VACUUM — отсюда bloat.
- **HOT**: индексированные колонки не менялись и есть место на странице → индексы не трогаются. Помогают `fillfactor` и отказ от лишних индексов.
- **VACUUM** освобождает место внутри файла, **VACUUM FULL** переписывает файл, меняя ctid, под эксклюзивной блокировкой.
</Takeaways>
