MVCC избавляет читателей и писателей от взаимного ожидания, но блокировки в Postgres никуда не делись. Они защищают **структуру таблиц** от одновременных изменений и **строки** — от одновременной записи. Самые болезненные инциденты с Postgres в проде — не медленные запросы, а миграции, которые подвесили таблицу.

## Блокировки таблиц

Восемь уровней, от слабого к сильному. Главные:

| Уровень | Кто берёт | Несовместим с |
|---|---|---|
| `AccessShare` | `SELECT` | только `AccessExclusive` |
| `RowExclusive` | `INSERT`, `UPDATE`, `DELETE` | `Share` и сильнее |
| `ShareUpdateExclusive` | `VACUUM`, `CREATE INDEX CONCURRENTLY`, `ANALYZE` | себя и сильнее |
| `Share` | `CREATE INDEX` (без CONCURRENTLY) | любую запись |
| `AccessExclusive` | `ALTER TABLE` (большинство), `DROP`, `TRUNCATE`, `VACUUM FULL` | **всё**, даже `SELECT` |

Важный вывод: обычный `CREATE INDEX` блокирует запись в таблицу на всё время построения. В проде — только `CREATE INDEX CONCURRENTLY`.

## Очередь: почему мгновенный ALTER кладёт прод

Блокировки выдаются по очереди. Новый запрос не может «перепрыгнуть» того, кто уже ждёт несовместимую с ним блокировку — иначе ожидающий мог бы голодать вечно. Пройди сценарий:

Добавление nullable-колонки занимает миллисекунду. Но если таблицу держит долгий запрос, `ALTER TABLE` ждёт его, а **все остальные запросы встают за ALTER**. Таблица мертва, пока не закончится самый долгий запрос.

Правила безопасных миграций:

- всегда `SET lock_timeout = '2s'` (или меньше) перед DDL и повтор при неудаче;
- `CREATE INDEX CONCURRENTLY`, `ALTER TABLE … ADD CONSTRAINT … NOT VALID` + отдельный `VALIDATE CONSTRAINT`;
- изменения, переписывающие таблицу (смена типа колонки), — через новую колонку, фоновое копирование и переключение;
- `statement_timeout` и `idle_in_transaction_session_timeout` для приложения, чтобы долгие транзакции не держали блокировки.

## Блокировки строк

`UPDATE`/`DELETE` и `SELECT … FOR UPDATE` блокируют **строки**. Информация о блокировке хранится прямо в кортеже (`xmax`), а не в общей таблице, поэтому можно заблокировать миллионы строк без расхода памяти. Режимы:

- `FOR UPDATE` — собираюсь изменить или удалить; самый сильный;
- `FOR NO KEY UPDATE` — берёт обычный `UPDATE`, если не меняется ключ;
- `FOR SHARE` / `FOR KEY SHARE` — читаю и не хочу, чтобы строку удалили (так проверяются внешние ключи).

Полезные модификаторы: `NOWAIT` (сразу ошибка вместо ожидания) и **`SKIP LOCKED`** — пропустить занятые строки. На `SKIP LOCKED` строят очереди задач прямо в Postgres:

```sql
UPDATE jobs SET status = 'running', worker = $1
WHERE id = (
  SELECT id FROM jobs WHERE status = 'queued'
  ORDER BY id LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

## Deadlock

Две транзакции ждут друг друга: A заблокировала строку 1 и ждёт 2, B заблокировала 2 и ждёт 1. Postgres проверяет граф ожиданий через `deadlock_timeout` (1 с) и откатывает одну из транзакций с ошибкой `40P01`. Профилактика — **брать блокировки в одном порядке** (например, переводы между счетами: всегда сначала меньший id) и держать транзакции короткими.

<Callout kind="tip" title="Диагностика в проде">
Кто кого ждёт: `SELECT pid, pg_blocking_pids(pid), wait_event_type, state, query FROM pg_stat_activity WHERE wait_event_type = 'Lock'`. Включи `log_lock_waits = on` — в лог попадут ожидания дольше `deadlock_timeout`.
</Callout>

<Takeaways>
- Табличные блокировки: `SELECT` — AccessShare, запись — RowExclusive, большинство `ALTER` — **AccessExclusive** (несовместим со всем).
- Очередь блокировок FIFO: ждущий ALTER блокирует **все** новые запросы → всегда `lock_timeout` для DDL.
- Индексы — `CONCURRENTLY`, ограничения — `NOT VALID` + `VALIDATE`.
- Строки: `FOR UPDATE` / `SHARE`, `NOWAIT`, **`SKIP LOCKED`** для очередей задач.
- Deadlock → `40P01`; брать блокировки в одном порядке, транзакции — короткие.
</Takeaways>
