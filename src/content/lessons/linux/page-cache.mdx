«На сервере 64 ГБ, а `free` показывает свободными 500 МБ — у нас утечка?» Нет: Linux использует всю незанятую память как **кэш файлов**. Понимать page cache нужно, чтобы правильно читать метрики памяти, понимать, когда данные действительно на диске, и почему базы данных так заботятся о `fsync`.

## Чтение и запись идут через кэш

- `read()` сначала смотрит в page cache. Нет — ядро читает страницы с диска, кладёт в кэш и копирует в буфер процесса. Повторное чтение — из памяти, в тысячи раз быстрее.
- `write()` только копирует данные в page cache и помечает страницы **грязными**. Возврат из `write` **не значит**, что данные на диске.
- Ядро сбрасывает грязные страницы в фоне (через ~30 секунд или при накоплении) — **writeback**.
- **`fsync(fd)`** ждёт, пока все грязные страницы файла (и метаданные) окажутся на диске. Только после него запись переживёт отключение питания.

## Что это значит на практике

- **`free -h`**: смотри на колонку `available`, а не `free`. `buff/cache` — это page cache, его ядро отдаст приложениям по первому требованию.
- **Базы данных** вызывают `fsync` на COMMIT (Postgres — для WAL). Без него «подтверждённая» транзакция может исчезнуть. Диски и контроллеры, которые врут про `fsync` (кэш записи без батареи), — источник потерянных данных.
- **Postgres и двойное кэширование**: страница может лежать и в shared_buffers, и в page cache. Поэтому shared_buffers ставят ~25% RAM, а остальное оставляют ОС.
- **Kafka** опирается на page cache почти целиком: пишет последовательно, читает свежие сообщения прямо из кэша, а `sendfile` отдаёт их в сокет без копирования в пространство пользователя (zero-copy).
- **`mmap`** отображает файл прямо в адресное пространство: обращение к странице — page fault, ядро подгружает её из кэша/диска. Так работают SQLite, LMDB, загрузка весов моделей.
- **O_DIRECT** — мимо page cache, для систем со своим кэшем (некоторые СУБД).

<Callout kind="warn" title="Грязные страницы и задержки">
Если приложение пишет быстрее, чем диск успевает, грязных страниц становится много, и ядро начинает тормозить пишущие процессы (`dirty_ratio`). Отсюда внезапные паузы записи в логах на секунды. Параметры `vm.dirty_background_ratio` / `vm.dirty_ratio` (или `*_bytes`) регулируют, когда начинается фоновая запись и когда блокировка.
</Callout>

<Takeaways>
- Вся свободная память — **page cache**; смотри `available`, а не `free`.
- `read` — из кэша или с диска в кэш; `write` — в кэш, страницы **грязные**.
- Данные на диске только после **`fsync`**; базы вызывают его на COMMIT.
- mmap, sendfile (zero-copy), O_DIRECT — разные способы работать с кэшем.
- Много грязных страниц → блокировка писателей (`dirty_ratio`).
</Takeaways>
