Тесты пишут не ради процента покрытия и не ради ревьюера. Их настоящая цель — **менять код без страха**. Сервис без тестов боятся трогать: каждое изменение — лотерея, рефакторинг откладывается, код гниёт. Сервис с хорошими тестами можно переписывать по кусочку каждый день.

## Пирамида и её критика

| Уровень | Что проверяет | Скорость | Сколько |
|---|---|---|---|
| **Юнит** | один класс или функция, без сети и базы | миллисекунды | много |
| **Интеграционный** | связку с настоящими зависимостями: база, брокер, HTTP | секунды | заметно меньше |
| **Сквозной (E2E)** | весь путь пользователя через UI или API | десятки секунд | единицы |

Логика пирамиды: внизу тесты дешёвые и точно показывают, что сломалось; наверху дорогие, медленные и «моргающие». Современная критика: в бэкенде, где основная логика — это SQL, транзакции и интеграции, юнит-тесты на моках проверяют мало. Отсюда **«сота»** (honeycomb) у микросервисов: основной слой — интеграционные тесты сервиса с настоящей базой в контейнере. Правило вместо догмы: **тестируй на том уровне, где живёт риск**.

## Хороший тест

1. **Проверяет поведение, а не реализацию.** Тест не должен ломаться от рефакторинга, который не меняет поведение. Тест, который проверяет, что метод `save` вызван ровно один раз с ровно такими аргументами, ломается от каждой перестановки кода.
2. **Падает по одной причине и понятно.** Имя `rejectsTransferWhenBalanceIsInsufficient`, а не `test3`.
3. **Детерминирован.** Никаких `Thread.sleep`, текущего времени, случайных портов и порядка выполнения тестов. Время — через `Clock`, случайность — через seed.
4. **Быстрый.** Набор, который идёт 20 минут, перестают запускать.
5. **Проверяет что-то.** Покрытие 100% ничего не гарантирует, если в тестах нет проверок. Убедись сам:

**Мутационное тестирование** вносит в код маленькие ошибки (поменять `>=` на `>`, `&&` на `||`, вернуть константу) и смотрит, упадут ли тесты. Выживший мутант — место, которое тесты на самом деле не проверяют. В Java — инструмент PIT.

## Что тестировать в первую очередь

- **Бизнес-правила и инварианты** — деньги, права, статусы.
- **Границы**: 0, 1, пустая коллекция, максимум, ровно на пороге.
- **Ошибки**: что происходит при отказе базы, таймауте, невалидном вводе.
- **То, что уже ломалось**: каждый баг из прода — сначала тест, который его воспроизводит, потом исправление.

Что тестировать не нужно: геттеры, сеттеры, код фреймворка, тривиальные пробросы.

## Карта трека

1. **Юнит-тесты и двойники** — AAA, stub, mock, fake; почему моки часто вредят.
2. **TDD** — цикл «красный — зелёный — рефакторинг».
3. **Интеграционные тесты** — Testcontainers, Spring Boot Test, контракты.

<Takeaways>
- Цель тестов — **менять код без страха**, а не процент покрытия.
- **Пирамида**: много быстрых юнит-тестов, меньше интеграционных, мало E2E. Для бэкенда с базой — «сота»: упор на интеграционные тесты сервиса. Тестируй там, где риск.
- Хороший тест: проверяет **поведение**, падает по одной понятной причине, детерминирован, быстрый.
- **Покрытие ≠ качество**; мутационное тестирование (PIT) показывает непроверенные места.
- Приоритет: бизнес-правила, границы, ошибки, прошлые баги.
</Takeaways>
