Юнит-тест проверяет небольшую единицу поведения изолированно — без сети, базы и файлов — и выполняется за миллисекунды. Чтобы изолировать код от тяжёлых зависимостей, их подменяют **тестовыми двойниками**. Именно с двойниками связано большинство плохих тестов.

## Структура: Arrange — Act — Assert

```java
@Test
void transferMovesMoneyBetweenAccounts() {
    // Arrange: подготовили мир
    var from = Account.open(Money.of(1000));
    var to = Account.open(Money.ZERO);
    var service = new TransferService(new InMemoryAccounts(from, to), Clock.fixed(NOON, UTC));

    // Act: одно действие
    service.transfer(from.id(), to.id(), Money.of(300));

    // Assert: проверили результат
    assertThat(from.balance()).isEqualTo(Money.of(700));
    assertThat(to.balance()).isEqualTo(Money.of(300));
}
```

Один тест — одно поведение. Если в тесте несколько «Act», это несколько тестов. Имя теста — предложение о поведении: `transferMovesMoneyBetweenAccounts`, `rejectsTransferToSameAccount`.

## Когда моки вредят

Мок проверяет **взаимодействие**: «метод X вызван с аргументами Y». Такой тест знает, **как** код устроен внутри, и ломается при любом рефакторинге, даже если поведение не изменилось.

Две школы:
- **Классическая (детройтская)**: юнит — это единица **поведения**, может включать несколько настоящих классов; двойники — только для медленного и внешнего.
- **Лондонская (mockist)**: юнит — один класс, все соседи — моки. Тесты точнее локализуют ошибку, но хрупче.

На практике в бэкенде побеждает классическая школа с фейками и Testcontainers.

## Время, случайность, UUID

Нестабильные тесты почти всегда зависят от недетерминированного окружения. Делай его зависимостью:

```java
class TokenService {
    private final Clock clock;            // не LocalDateTime.now()
    private final Supplier<UUID> ids;     // не UUID.randomUUID()
    TokenService(Clock clock, Supplier<UUID> ids) { ... }
}
// в тесте
new TokenService(Clock.fixed(Instant.parse("2025-03-08T10:00:00Z"), UTC), () -> FIXED_ID);
```

## Параметризованные тесты для границ

```java
@ParameterizedTest
@CsvSource({ "17, false", "18, true", "65, true", "0, false" })
void ageLimit(int age, boolean allowed) {
    assertThat(policy.canBuy(age)).isEqualTo(allowed);
}
```

Одна проверка — много случаев, особенно граничных. Ещё мощнее — **property-based testing** (jqwik): генератор сам подбирает входы и ищет контрпример к свойству вроде «разбиение суммы на части всегда даёт исходную сумму».

<Takeaways>
- Структура **Arrange — Act — Assert**, одно поведение на тест, имя — предложение о поведении.
- Двойники: **dummy, stub, mock, spy, fake**. Fake (in-memory реализация) часто лучший выбор.
- **Мок проверяет взаимодействие** — это хрупко. Мокай внешние побочные эффекты, остальное — фейки или настоящие объекты.
- Время, случайность, id — через зависимости (`Clock`, `Supplier<UUID>`): тесты детерминированы.
- **Параметризованные** тесты для границ, **property-based** — для свойств.
</Takeaways>
