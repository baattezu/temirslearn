Юнит-тесты на моках не скажут, что SQL-запрос неверен, миграция ломает схему, индекс не используется, а транзакция ведёт себя не так, как ты думал. Это проверяют **интеграционные тесты** — с настоящими зависимостями. Раньше это было мучительно: общая тестовая база, которую все портят, или H2 в памяти, который ведёт себя не как Postgres. Сейчас есть Testcontainers.

## Почему не H2

Встраиваемая база в памяти кажется удобной, но это другая СУБД:
- другой SQL-диалект: `jsonb`, `ON CONFLICT`, оконные функции, массивы — работают в Postgres и падают в H2 (или наоборот);
- другие уровни изоляции и блокировки — тесты на конкурентность бессмысленны;
- тест зелёный, прод падает — худший вид ложной уверенности.

Правило: **тестируй на той же базе, что в проде**.

## Testcontainers

Библиотека запускает настоящий Postgres (Kafka, Redis, LocalStack…) в Docker прямо из теста и выключает после.

```java
@SpringBootTest
@Testcontainers
class OrderRepositoryIT {

    @Container
    @ServiceConnection                          // Spring Boot 3.1+: сам пропишет url, user, password
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:17");

    @Autowired OrderRepository orders;

    @Test
    void findsPaidOrdersOfCustomer() {
        orders.save(order(CUSTOMER, PAID));
        orders.save(order(CUSTOMER, CANCELLED));

        assertThat(orders.findPaidByCustomer(CUSTOMER)).hasSize(1);
    }
}
```

Миграции (Flyway/Liquibase) применяются при старте контекста — значит, проверяются и они. Контейнер один на класс (`static`), а с `reuse` — и между запусками.

## Срезы Spring Boot Test

Поднимать весь контекст на каждый тест дорого. Spring Boot умеет поднимать только нужный слой:

| Аннотация | Что поднимает | Для чего |
|---|---|---|
| `@WebMvcTest` | контроллеры, Jackson, валидацию; сервисы — моки | HTTP-контракт: статусы, JSON, ошибки |
| `@DataJpaTest` | JPA, репозитории, базу | запросы, маппинг, ограничения |
| `@JsonTest` | только сериализацию | формат JSON |
| `@SpringBootTest` | всё приложение | сквозные сценарии сервиса |

Контекст Spring кэшируется между тестами с одинаковой конфигурацией — поэтому не плоди уникальные `@MockBean` в каждом классе: каждая комбинация — новый контекст и лишние секунды.

## Изоляция тестов

Тесты не должны зависеть друг от друга и от порядка запуска:
- `@Transactional` на тесте откатывает изменения после теста — удобно, но **маскирует** проблемы: не срабатывают `AFTER_COMMIT`-слушатели, не видно поведения после коммита, lazy-загрузка работает «чудом»;
- надёжнее — чистить таблицы перед тестом (`TRUNCATE`) или создавать уникальные данные на тест.

## Контрактные тесты между сервисами

Сервис A вызывает сервис B. Поднимать оба в тестах дорого, а мокать B — значит рисковать, что мок разошёлся с реальностью. **Контрактные тесты** (Pact, Spring Cloud Contract):
- потребитель описывает ожидания: «на `GET /users/42` жду 200 и поля id, email»;
- поставщик в своём CI проверяет, что выполняет все контракты потребителей.

Сломал поле, на которое кто-то рассчитывает, — красный билд у тебя, а не инцидент в проде.

## Что ещё

- **Нестабильные тесты** (flaky) — чинить или удалять сразу: к красному билду, который «иногда просто падает», привыкают и перестают замечать настоящие поломки.
- **Внешние HTTP-API** — WireMock: поднимает фейковый сервер с заданными ответами, включая таймауты и 500.
- **Время сборки**: интеграционные тесты медленнее — их запускают параллельно и отдельной фазой (`*IT` через Maven Failsafe).

<Takeaways>
- Интеграционные тесты ловят то, что не видно моками: SQL, миграции, транзакции, сериализацию.
- **Не H2** — тестируй на той же СУБД, что в проде; **Testcontainers** + `@ServiceConnection`.
- Срезы: `@WebMvcTest`, `@DataJpaTest`, `@SpringBootTest`; не плоди уникальные конфигурации — кэш контекста.
- Изоляция: `@Transactional` на тесте удобен, но маскирует поведение после коммита.
- Между сервисами — **контрактные тесты**; внешние API — WireMock; flaky-тесты чинить сразу.
</Takeaways>
