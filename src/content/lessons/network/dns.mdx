Перед любым HTTP-запросом нужно превратить имя в IP-адрес. DNS — это распределённая иерархическая база, где за каждый уровень имени отвечают свои серверы, а всё держится на **кэшировании**. Когда «всё сломалось» — часто это DNS.

## Иерархия

Имя читается справа налево: `temirslearn.verylabs.dev.` — корень `.` → зона `dev` → зона `verylabs.dev` → запись `temirslearn`.

- **Корневые серверы** (13 имён, сотни anycast-копий) знают, кто отвечает за каждую зону верхнего уровня.
- **TLD-серверы** (`.dev`, `.com`, `.kz`) знают, какие NS-серверы отвечают за домены второго уровня.
- **Авторитативные серверы** домена хранят его записи. Для `verylabs.dev` это Cloudflare.

## Кто делает работу

- **Stub resolver** в ОС умеет только спросить один рекурсивный резолвер и подождать.
- **Рекурсивный резолвер** (провайдера, 1.1.1.1, 8.8.8.8, CoreDNS в Kubernetes) проходит иерархию сам и кэширует каждый ответ на его **TTL**.

С холодным кэшем — несколько последовательных запросов через интернет, десятки-сотни миллисекунд. С тёплым — ответ из памяти резолвера. Именно поэтому новые домены «открываются не сразу» (кэш негативного ответа), а смена IP расползается по миру со скоростью TTL.

## Записи

| Тип | Что хранит |
|---|---|
| `A` / `AAAA` | IPv4 / IPv6 адрес |
| `CNAME` | «это имя — псевдоним другого имени» (нельзя на корне зоны) |
| `NS` | какие серверы авторитативны для зоны |
| `MX` | почтовые серверы |
| `TXT` | произвольный текст: SPF, DKIM, подтверждение владения доменом |
| `SRV` | хост и порт сервиса |
| `CAA` | какие центры сертификации могут выпускать сертификаты |

## DNS в эксплуатации

- **TTL перед миграцией**: за день до смены IP снизь TTL до 60 с, после — верни.
- **Негативное кэширование**: ответ «такого имени нет» (NXDOMAIN) тоже кэшируется — на время из SOA-записи зоны. Отсюда эффект «создал поддомен, а у меня не открывается, у коллеги открывается» — локальный кэш помнит, что имени не было (как было у тебя с temirslearn).
- **Балансировка через DNS**: несколько A-записей, GeoDNS, но клиенты кэшируют и игнорируют TTL — для быстрого переключения не годится.
- **В Kubernetes**: `ndots:5` в `/etc/resolv.conf` пода заставляет имя `api.example.com` сначала пройти поиск по всем search-доменам кластера — лишние запросы и задержки. Пиши полные имена с точкой на конце или уменьши `ndots`.

<Callout kind="tip" title="Диагностика">
`dig temirslearn.verylabs.dev +trace` проходит иерархию сам, как резолвер. `dig @1.1.1.1 name` — спросить конкретный резолвер. В Chrome — `chrome://net-internals/#dns` для сброса кэша браузера, в macOS — `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`.
</Callout>

<Takeaways>
- Имя резолвится по иерархии: **корень → TLD → авторитативный**; работу делает **рекурсивный резолвер**.
- Каждый ответ кэшируется на **TTL**, в том числе отрицательный (NXDOMAIN).
- Записи: A/AAAA, CNAME, NS, MX, TXT, SRV, CAA.
- Перед миграцией снижай TTL; DNS-балансировка медленно переключается.
- `dig +trace` — главный инструмент диагностики.
</Takeaways>
