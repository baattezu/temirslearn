Контейнер — это не виртуальная машина. Это **обычный процесс Linux**, которому ядро показывает урезанный мир: свои PID, сеть, файловую систему и лимиты ресурсов. Всё, что делает Docker, собрано из трёх механизмов ядра: namespaces, cgroups и overlayfs.

## Namespaces: что процесс видит

| Namespace | Изолирует |
|---|---|
| `pid` | номера процессов: внутри контейнера твой процесс — PID 1 |
| `net` | сетевые интерфейсы, IP, порты, таблицы маршрутизации |
| `mnt` | точки монтирования — своя корневая ФС |
| `uts` | hostname |
| `ipc` | разделяемая память, очереди сообщений |
| `user` | соответствие UID: root внутри может быть обычным пользователем снаружи |
| `cgroup` | вид на иерархию cgroups |

Снаружи контейнер виден как обычный процесс: `ps aux` на хосте покажет его, `docker top` — тоже.

## cgroups: сколько процесс может потратить

Control groups ограничивают и учитывают ресурсы: CPU (квота — например, 0.5 ядра), память (жёсткий лимит), I/O, число процессов. Превысил лимит памяти — **OOM killer** убивает процесс внутри cgroup (в Kubernetes это `OOMKilled`). Ограничение CPU работает через квоты: процесс, исчерпавший квоту за период 100 мс, **троттлится** до конца периода — отсюда странные задержки в p99 у контейнеров с маленьким CPU limit.

<Callout kind="warn" title="Лимиты и рантаймы">
Старые JVM и рантаймы смотрели на память и ядра **хоста**, а не cgroup, и выделяли heap больше лимита. Современная JVM понимает cgroups (`-XX:+UseContainerSupport` по умолчанию), но `-Xmx` всё равно должен оставлять место под metaspace, стеки и direct memory. Node.js, Go (`GOMAXPROCS`) и Python-воркеры тоже надо подстраивать под лимиты.
</Callout>

## Образ — это слои

Образ состоит из **слоёв**: каждая инструкция `RUN`, `COPY`, `ADD` в Dockerfile создаёт слой — архив изменений файловой системы. Слои адресуются по хешу содержимого и **переиспользуются**: между сборками (кэш) и между образами (общий базовый образ хранится один раз).

Правила хорошего Dockerfile:

- от редко меняющегося к часто меняющемуся: зависимости до кода;
- `.dockerignore` (без `.git`, `node_modules`, артефактов) — иначе `COPY . .` инвалидируется любым изменением;
- **multi-stage**: собрать в образе с компиляторами, а в финальный скопировать только бинарник/jar;
- один `RUN` для установки и очистки (`apt-get install … && rm -rf /var/lib/apt/lists/*`) — удаление в следующем слое не уменьшает образ.

## Контейнер = образ + тонкий слой для записи

При запуске поверх слоёв образа (только для чтения) монтируется **overlayfs** с пустым верхним слоем для записи:

<OverlayFs />

- изменение файла из образа — **copy-up**: файл копируется в верхний слой целиком;
- удаление — **whiteout**-файл, который скрывает нижний; образ не уменьшается;
- верхний слой исчезает вместе с контейнером. Данные, которые надо сохранить, — в **volume** (монтируется мимо overlayfs, и запись в него быстрее).

<Takeaways>
- Контейнер — **процесс** с namespaces (что видит) и cgroups (сколько тратит). Ядро общее с хостом.
- Лимит памяти → OOMKilled; лимит CPU → троттлинг. Рантаймы должны знать о лимитах.
- Образ — **слои** по хешу; кэш сборки ломается с первого изменённого слоя → зависимости раньше кода.
- Контейнер — слои образа (ro) + **верхний rw-слой** overlayfs: copy-up, whiteout, исчезает с контейнером.
- Данные — в volume; образы — multi-stage и `.dockerignore`.
</Takeaways>
