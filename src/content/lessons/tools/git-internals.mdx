Git кажется набором загадочных команд, пока не увидишь, что внутри он устроен очень просто: **хранилище объектов, адресуемых по хешу содержимого**, и несколько текстовых файлов-указателей. После этого `rebase`, `reset`, «потерянные» коммиты и detached HEAD перестают пугать.

## Четыре типа объектов

Всё лежит в `.git/objects`, имя объекта — SHA-1 (в новых репозиториях может быть SHA-256) от его содержимого:

- **blob** — содержимое файла. Без имени и прав — только байты;
- **tree** — каталог: список «имя → blob или tree + права»;
- **commit** — ссылка на корневой tree, родители, автор, время, сообщение;
- **tag** — аннотированный тег с подписью.

Поскольку имя = хеш содержимого, одинаковые файлы хранятся один раз, а любое изменение где угодно меняет хеш дерева, а значит, и коммита. Подделать историю незаметно нельзя.

Посмотреть руками:

```bash
git cat-file -p HEAD            # commit: tree, parent, author, message
git cat-file -p HEAD^{tree}     # tree: blob'ы и поддеревья
git cat-file -p <blob-hash>     # содержимое файла
```

## Ветка — это файл с хешем

`refs/heads/main` — текстовый файл из 40 символов хеша. Создать ветку — записать файл. **HEAD** — указатель на текущую ветку (`ref: refs/heads/main`) или прямо на коммит (это и есть detached HEAD). Коммит создаёт новый объект и передвигает указатель текущей ветки.

## merge и rebase

- **Fast-forward**: если текущая ветка — предок вливаемой, merge просто сдвигает указатель. Новых коммитов нет.
- **Merge commit**: если ветки разошлись, создаётся коммит с **двумя родителями**. История сохраняется как была, с «ромбом».
- **Rebase** берёт твои коммиты и **создаёт новые** поверх другой ветки: у них другой родитель, значит, другие хеши. Старые коммиты никуда не делись, но на них больше не указывает ни одна ветка.

Отсюда золотое правило: **не делай rebase коммитов, которые уже кто-то забрал** — у них в истории старые хеши, и после твоего `push --force` истории разойдутся.

<Callout kind="tip" title="Ничего не теряется сразу">
Недостижимые коммиты живут, пока их не уберёт `git gc` (по умолчанию через 2 недели для «висячих» объектов и 90 дней для записей reflog). `git reflog` показывает, куда указывал HEAD раньше: после неудачного `reset --hard` или rebase можно вернуться через `git reset --hard HEAD@{2}`.
</Callout>

## reset, checkout, restore — на языке указателей

| Команда | Что двигает |
|---|---|
| `git reset --soft X` | только указатель ветки на X |
| `git reset --mixed X` (по умолчанию) | ветку + индекс |
| `git reset --hard X` | ветку + индекс + рабочие файлы |
| `git switch other` | HEAD на другую ветку + файлы |
| `git restore file` | только файл из индекса или коммита |

**Индекс** (staging area, `.git/index`) — это будущий tree следующего коммита: `git add` кладёт blob в хранилище и записывает его хеш в индекс.

<Takeaways>
- Git — **хранилище объектов по хешу**: blob (файл), tree (каталог), commit (tree + родители + метаданные).
- Одинаковое содержимое хранится один раз; изменение любого байта меняет хеши вверх до коммита.
- **Ветка** — файл с хешем, **HEAD** — указатель на ветку (или на коммит = detached).
- merge: fast-forward или коммит с двумя родителями; **rebase пересоздаёт коммиты с новыми хешами**.
- Ничего не теряется сразу: **reflog** + `reset --hard HEAD@{n}`.
</Takeaways>
