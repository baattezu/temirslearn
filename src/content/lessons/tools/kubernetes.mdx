Kubernetes часто объясняют списком сущностей: pod, deployment, service, ingress. Но понимать его проще через одну идею: **ты описываешь желаемое состояние, а контроллеры бесконечно приводят к нему фактическое**. Почти всё поведение Kubernetes — следствие этого цикла.

## Архитектура

**Control plane**:

- **kube-apiserver** — единственная точка входа. Все (kubectl, контроллеры, kubelet) читают и пишут состояние через него.
- **etcd** — распределённое key-value хранилище (Raft). Здесь лежит всё желаемое и наблюдаемое состояние кластера.
- **scheduler** — для подов без узла выбирает узел: фильтрует по ресурсам, affinity, taints, потом ранжирует.
- **controller-manager** — десятки контроллеров: ReplicaSet, Deployment, Node, Job, EndpointSlice…

**На каждом узле**:

- **kubelet** — смотрит, какие поды назначены на его узел, и запускает их через container runtime (containerd), проверяет пробы, сообщает статус.
- **kube-proxy** (или eBPF в Cilium) — правила, по которым трафик на Service попадает в поды.

## Сущности, которые надо знать

| Сущность | Зачем |
|---|---|
| **Pod** | один или несколько контейнеров с общей сетью (один IP) и томами. Смертен и заменяем. |
| **Deployment** → ReplicaSet | N одинаковых подов + rolling update с откатом |
| **StatefulSet** | стабильные имена и диски для баз и брокеров |
| **DaemonSet** | по поду на каждый узел (сбор логов, агенты) |
| **Service** | стабильный виртуальный IP и DNS-имя перед меняющимся набором подов |
| **Ingress / Gateway** | HTTP-маршрутизация снаружи в сервисы |
| **ConfigMap / Secret** | конфигурация и секреты в виде файлов или переменных |

## Пробы и ресурсы — источник большинства инцидентов

- **readinessProbe**: под не готов — его убирают из Service, трафик не идёт. **livenessProbe**: провалилась — контейнер перезапускают. Частая ошибка — liveness, которая проверяет базу: база тормозит → все поды перезапускаются разом → полный отказ. Liveness должна проверять только сам процесс.
- **requests** — сколько ресурса резервирует scheduler при размещении. **limits** — потолок: CPU выше лимита троттлится, память выше лимита — OOMKilled.
- **Rolling update**: `maxSurge` / `maxUnavailable` определяют, сколько подов меняется одновременно; с readiness-пробой новая версия получает трафик только когда готова. Graceful shutdown: на SIGTERM перестать принимать запросы и доделать текущие за `terminationGracePeriodSeconds`.

<Takeaways>
- Kubernetes = **желаемое состояние в etcd** + **контроллеры**, которые сводят к нему фактическое.
- apiserver — единственная дверь; scheduler выбирает узел; kubelet запускает поды на узле.
- Level-triggered: реакция на разницу, а не на события → самовосстановление.
- Pod смертен; стабильность дают Deployment (реплики, rolling update) и Service (стабильный адрес).
- readiness — убрать из трафика, liveness — перезапуск (не проверять ею зависимости!). requests — для планирования, limits — троттлинг и OOMKilled.
</Takeaways>
