Браузер превращает HTML, CSS и JS в пиксели десятки раз в секунду. Если понимать этапы, становится ясно, почему одни анимации плавные, а другие дёргаются, и почему чтение `offsetHeight` в цикле может повесить страницу.

## Процессы Chrome

Chrome — многопроцессный:

- **browser process** — вкладки, адресная строка, сеть, диск;
- **renderer process** на сайт (site isolation) — парсинг, JS, layout, paint. В песочнице: даже взломанный рендерер не читает файлы и не видит другие сайты;
- **GPU process** — общается с видеокартой, собирает итоговый кадр;
- отдельные процессы для расширений, сети, аудио.

Внутри рендерера главное — **main thread** (JS, стили, layout, paint) и **compositor thread** (сборка слоёв и прокрутка).

## Конвейер кадра

1. **Parse**: HTML → DOM, CSS → CSSOM. Скрипт без `defer`/`async` останавливает парсер.
2. **Style**: для каждого узла вычислить итоговые стили.
3. **Layout**: посчитать геометрию — где каждый блок и какого размера. Изменение одного элемента может сдвинуть всех соседей.
4. **Paint**: записать список команд рисования (прямоугольники, текст, тени) по слоям.
5. **Composite**: растеризовать слои в текстуры и собрать кадр на GPU — в compositor thread, независимо от main thread.

## Правила плавного интерфейса

- Анимируй **`transform` и `opacity`** — они обходят layout и paint, а compositor продолжает работать, даже если JS занят. `will-change: transform` заранее выносит элемент на свой слой (но каждый слой — память GPU, не злоупотребляй).
- **Не перемешивай чтения и записи геометрии**. Запись стиля помечает layout «грязным», а чтение `offsetHeight`, `getBoundingClientRect`, `scrollTop` заставляет посчитать его прямо сейчас (forced synchronous layout). Сначала все чтения, потом все записи, или `requestAnimationFrame`.
- **Изменения DOM пачкой**: DocumentFragment, виртуализация длинных списков (рендерить только видимые строки), `content-visibility: auto` для невидимых частей страницы.

## Критический путь загрузки

Первую отрисовку задерживает всё, что блокирует парсер и построение CSSOM:

- CSS в `<head>` — блокирует отрисовку (без него страница «прыгнула» бы). Минимальный критический CSS — инлайн, остальное позже;
- `<script>` без `defer` — блокирует парсинг. `defer` выполняет после парсинга по порядку, `async` — как только загрузится;
- шрифты — `font-display: swap`, чтобы текст не был невидимым;
- изображения — с размерами (`width`/`height`), иначе после загрузки всё съедет (CLS).

Метрики Core Web Vitals: **LCP** (когда отрисован самый большой элемент, < 2.5 с), **INP** (отзывчивость, < 200 мс), **CLS** (сдвиги вёрстки, < 0.1).

<Takeaways>
- Chrome: browser / renderer (на сайт, в песочнице) / GPU процессы; в рендерере — main и compositor потоки.
- Кадр: **Style → Layout → Paint → Composite**; что запускается — зависит от изменённого свойства.
- `transform` и `opacity` — только composite; геометрия (`width`, `top`) — весь конвейер.
- **Layout thrashing**: не читай геометрию после записи в цикле.
- Критический путь: CSS блокирует отрисовку, скрипты — парсинг (`defer`/`async`); LCP, INP, CLS.
</Takeaways>
