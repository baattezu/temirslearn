JavaScript в браузере выполняется в **одном потоке**, который делит время между твоим кодом, обработкой событий и отрисовкой. Порядок, в котором всё это происходит, — event loop. Вопрос «что выведет этот код» на фронтенд-собесе — почти обязательный, а непонимание event loop — главная причина подвисающих интерфейсов.

## Один оборот цикла

1. Взять **одну задачу** (task, macrotask) из очереди: скрипт, клик, ответ сети, таймер, `postMessage`.
2. Выполнить её до конца — пока стек вызовов не опустеет. Прервать её нельзя.
3. Выполнить **все микрозадачи** (`Promise.then`, продолжения после `await`, `queueMicrotask`, `MutationObserver`). Если микрозадача добавляет новые микрозадачи, они тоже выполняются сейчас.
4. Если пора рисовать кадр (обычно раз в ~16 мс при 60 Гц): колбэки `requestAnimationFrame` → пересчёт стилей → layout → paint → composite.
5. Повторить.

## Что из этого следует

- **Микрозадачи всегда раньше следующей задачи.** Поэтому `Promise.then` срабатывает раньше `setTimeout(…, 0)`.
- **`await` — это микрозадача.** Код после `await` продолжится в фазе микрозадач, после того как отработает остальной синхронный код вызывающего.
- **Бесконечные микрозадачи вешают страницу** так же, как бесконечный цикл: отрисовка не наступит, пока их очередь не пуста.
- **Изменения DOM в рамках одной задачи не видны пользователю по отдельности.** Браузер рисует только между задачами — поэтому «показать спиннер, посчитать 3 секунды, скрыть спиннер» в одной задаче не покажет спиннер никогда.

## Долгие задачи и INP

Задача дольше 50 мс считается **long task**. Пока она идёт, браузер не может ни обработать клик, ни нарисовать кадр. Метрика **INP** (Interaction to Next Paint) из Core Web Vitals измеряет именно это: сколько прошло от взаимодействия до следующего кадра. Хорошо — до 200 мс.

Как не блокировать поток:

- **Разбить работу на куски** и отдавать управление между ними: `await scheduler.yield()` (или `setTimeout(0)` в старых браузерах). Между кусками браузер успеет обработать ввод и нарисовать кадр.
- **Вынести тяжёлое в Web Worker** — отдельный поток со своим event loop (так в temirslearn работает судья задач: Python в Pyodide крутится в воркере и не замораживает редактор).
- Анимации — через `requestAnimationFrame` или CSS `transform`/`opacity`, которые compositor рисует без главного потока.

<Callout kind="info" title="А в Node.js?">
Идея та же — один поток и очереди, но фазы другие (libuv): timers → pending callbacks → poll (ввод-вывод) → check (`setImmediate`) → close. Микрозадачи и `process.nextTick` выполняются между каждым колбэком. Поэтому порядок `setTimeout(0)` и `setImmediate` в главном модуле не определён, а внутри колбэка ввода-вывода `setImmediate` всегда первый.
</Callout>

<Takeaways>
- Один поток: **задача → все микрозадачи → (может быть) кадр → следующая задача**.
- Микрозадачи: `then`, `await`, `queueMicrotask` — всегда раньше `setTimeout(0)`.
- Задачу нельзя прервать; DOM рисуется только **между** задачами.
- Long task > 50 мс ломает отзывчивость (INP). Решения: дробить с `scheduler.yield()`, Web Worker, анимации на compositor.
</Takeaways>
