«В Python нет настоящей многопоточности» — полуправда. Потоки в Python настоящие, но в CPython байткод в каждый момент выполняет только один из них: мешает **GIL**. Понимание, когда это важно, а когда нет, решает выбор между `threading`, `multiprocessing` и `asyncio`.

## Что такое GIL

Global Interpreter Lock — мьютекс внутри интерпретатора CPython. Поток должен держать его, чтобы выполнять байткод. Зачем: подсчёт ссылок и внутренние структуры интерпретатора не потокобезопасны, а один глобальный замок делает однопоточный код быстрым и расширения на C — простыми.

Поток отпускает GIL:

- при **блокирующем вводе-выводе** (сеть, диск, `sleep`);
- в тяжёлых C-расширениях, которые сами его отпускают (NumPy, хеширование, сжатие);
- принудительно каждые ~5 мс (`sys.getswitchinterval()`), чтобы другие потоки тоже работали.

## Три модели на одной картинке

<GilTimeline />

| Задача | Выбор | Почему |
|---|---|---|
| Много сетевых запросов | `asyncio` или потоки | GIL отпускается на ожидании; asyncio держит тысячи соединений дешевле |
| Тяжёлые расчёты на чистом Python | `multiprocessing` / `ProcessPoolExecutor` | у каждого процесса свой GIL |
| Расчёты в NumPy/PyTorch | потоки подойдут | GIL отпущен внутри C-кода |
| Смешанное | asyncio + `run_in_executor` для блокирующего/CPU кода | цикл не блокируется |

## asyncio изнутри

- `async def` — функция-корутина; вызов возвращает объект корутины, а не результат.
- `await` — точка, где корутина **добровольно** отдаёт управление event loop'у, пока ждёт результат.
- Event loop — один поток, который крутит готовые к выполнению корутины и через `epoll`/`kqueue` узнаёт, какие сокеты готовы.
- Нет вытесняющей многозадачности: корутина, которая считает 2 секунды без `await` (или вызывает синхронный `requests.get`), **замораживает всё приложение**.

```python
async def fetch_all(urls):
    async with httpx.AsyncClient() as client:
        tasks = [client.get(u) for u in urls]
        return await asyncio.gather(*tasks)      # все запросы параллельно

async def handler():
    data = await fetch_all(URLS)
    result = await asyncio.to_thread(heavy_parse, data)   # CPU — в поток, цикл свободен
    return result
```

<Callout kind="info" title="Python без GIL">
С Python 3.13 есть экспериментальная сборка без GIL (free-threaded, PEP 703), в 3.14 она официально поддерживается. Потоки там выполняют байткод параллельно, но однопоточный код немного медленнее, а C-расширения должны быть к этому готовы. Для серверов на asyncio это мало что меняет; для CPU-кода на чистом Python — многое.
</Callout>

<Takeaways>
- **GIL**: байткод CPython в каждый момент выполняет один поток; отпускается на I/O, в C-расширениях и каждые ~5 мс.
- I/O — потоки или **asyncio**; CPU на чистом Python — **процессы**; NumPy — потоки подходят.
- asyncio — один поток и кооперативная многозадачность: блокирующий вызов или долгий расчёт без `await` вешает всё.
- CPU и синхронные библиотеки из async-кода — через `to_thread` / `run_in_executor`.
- Free-threaded Python (3.13+) убирает GIL, но пока не по умолчанию.
</Takeaways>
