Хеш-таблица — самая полезная структура на собесе: половина задач решается фразой «положим в HashMap». Но спрашивают и то, как она устроена: коллизии, load factor, resize, почему `equals` без `hashCode` ломает всё.

## Идея

Массив из `m` **бакетов**. Ключ превращается в число хеш-функцией, число — в индекс бакета: `index = hash(key) mod m`. Если хеш хороший, ключи распределяются равномерно, и в каждом бакете их в среднем `n / m` — это **load factor** α. Пока α ограничен константой, операции работают за O(1) в среднем.

Когда m — степень двойки, `mod m` превращается в дешёвую маску `hash & (m − 1)`. Но тогда в индекс попадают только **младшие биты** хеша. Поэтому Java перед этим подмешивает старшие биты: `h ^ (h >>> 16)`.

## Коллизии: два подхода

<HashTableViz />

**Цепочки** (Java `HashMap`, Go `map` в общих чертах): в бакете лежит список ключей. Коллизия просто удлиняет список. Удаление тривиально. В Java 8+, если цепочка становится длиннее 8 (а бакетов уже не меньше 64), она превращается в **красно-чёрное дерево** — защита от атак, когда злоумышленник подбирает ключи с одинаковым хешем.

**Открытая адресация** (Python `dict`, `HashMap` в Rust, Abseil `flat_hash_map`; а вот C++ `std::unordered_map` — на цепочках): всё лежит в одном массиве, по ключу на ячейку. При коллизии пробуем следующую ячейку. Плюсы — нет указателей и всё в кэше. Минусы:

- нельзя просто стереть ключ: поиск других ключей, прошедших через эту ячейку, оборвётся на пустоте. Нужно **надгробие** (tombstone);
- таблицу нельзя заполнять почти полностью: длина проб быстро растёт. Обычно resize при α ≈ 0.5–0.75.

Попробуй в режиме открытой адресации удалить ключ, а потом найти тот, что лежал за ним.

## Resize

Когда α превышает порог (у `HashMap` — 0.75), массив увеличивается вдвое, и **все ключи переразкладываются**: индекс зависит от m. Отдельная вставка стоит O(n), но, как у динамического массива, амортизированно — O(1). Если размер известен заранее — `new HashMap<>(expected * 4 / 3 + 1)` (или `HashMap.newHashMap(n)` в Java 19+).

## Контракт hashCode и equals

1. Равные объекты (`equals`) **обязаны** иметь равный `hashCode`. Иначе `map.get(k)` ищет не в том бакете и возвращает `null` для существующего ключа.
2. Разные объекты **могут** иметь одинаковый хеш — это коллизия, она обрабатывается.
3. Ключ **нельзя менять** после вставки, если от этого меняется хеш. Объект «потеряется» в старом бакете. Поэтому ключи делают неизменяемыми: `String`, `record`, `Integer`.

<Callout kind="warn" title="Худший случай">
Все ключи в одном бакете → O(n) на операцию (с цепочками-деревьями в Java — O(log n)). Это реальная атака (HashDoS): POST-запрос с тысячами параметров, специально подобранных под одну корзину. Поэтому Python и Go используют **случайную соль** в хеш-функции строк при старте процесса.
</Callout>

## Шаблоны задач

| Задача | Приём |
|---|---|
| Two Sum | `seen[x] = i`; для каждого `x` ищем `target − x` |
| Группировка анаграмм | ключ = отсортированное слово или счётчик букв |
| Подмассив с суммой k | префиксные суммы + счётчик: сколько раз встречалась `prefix − k` |
| Первый неповторяющийся | два прохода: подсчёт, потом поиск |
| Длиннейшая последовательность | `set` + старт только с `x`, у которого нет `x − 1` → O(n) |

Во вкладке **Задачи**: Two Sum и Top K Frequent.

<Takeaways>
- Индекс = `hash(key) & (m − 1)`; среднее O(1) при ограниченном **load factor**.
- Коллизии: **цепочки** (Java HashMap, деревья при длине > 8) или **открытая адресация** (Python dict, надгробия при удалении).
- **Resize** ×2 при α > 0.75 — O(n) разово, O(1) амортизированно.
- Контракт: равные по `equals` → равный `hashCode`; ключи — неизменяемые.
- Худший случай O(n) — защита: деревья в бакетах, случайная соль хеша.
</Takeaways>
