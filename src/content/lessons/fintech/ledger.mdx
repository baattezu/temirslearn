Самая частая ошибка в первом финтех-проекте — таблица `accounts` с колонкой `balance`, которую обновляют при каждой операции: `UPDATE accounts SET balance = balance - 100`. Работает до первого инцидента: баланс не сходится, и **невозможно понять почему** — история изменений не сохранилась. Бухгалтеры решили эту задачу пятьсот лет назад.

## Двойная запись

В 1494 году **Лука Пачоли** описал метод, которым пользовались венецианские купцы: каждая операция записывается **дважды** — на одном счёте как дебет, на другом как кредит, и суммы равны. Сумма всех дебетов в книге всегда равна сумме всех кредитов. Если не равна — где-то ошибка, и это видно сразу.

Для разработчика это превращается в три правила:

1. **Проводка** (entry) состоит из нескольких строк (postings), и сумма строк равна нулю: сколько ушло с одних счетов, столько пришло на другие.
2. **Журнал только дописывается.** Проводки не меняют и не удаляют. Ошибку исправляют **сторнирующей** проводкой — новой записью с обратными знаками.
3. **Баланс не хранится, а вычисляется** как сумма проводок по счёту (или хранится как кэш, который всегда можно пересчитать и проверить).

## Почему кошелёк клиента — это обязательство

Самое контринтуитивное в учёте. Когда Алия кладёт 10 000 ₸ в кошелёк, у банка появляются **деньги** (актив, дебет) и одновременно **долг перед Алией** — банк обязан вернуть их по первому требованию (обязательство, кредит). Деньги клиентов — это не доход банка, а его долг. Доход банка — только комиссии.

Знаки в коде удобно договориться считать так: дебет — плюс, кредит — минус. Тогда у каждой проводки сумма строк — ноль, а у всего леджера сумма балансов — ноль.

## Схема в базе

```sql
CREATE TABLE accounts (
  id        BIGINT PRIMARY KEY,
  code      TEXT NOT NULL UNIQUE,         -- 'wallet:alice', 'fees:p2p'
  currency  CHAR(3) NOT NULL,
  kind      TEXT NOT NULL                 -- asset | liability | income | expense
);

CREATE TABLE entries (                    -- проводка: одна бизнес-операция
  id          BIGINT PRIMARY KEY,
  kind        TEXT NOT NULL,              -- 'p2p_transfer', 'refund', 'reversal'
  external_id TEXT UNIQUE,                -- ключ идемпотентности
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE postings (                   -- строки проводки
  entry_id    BIGINT NOT NULL REFERENCES entries(id),
  account_id  BIGINT NOT NULL REFERENCES accounts(id),
  amount      BIGINT NOT NULL,            -- минорные единицы; + дебет, − кредит
  PRIMARY KEY (entry_id, account_id)
);
-- инвариант проверяется при записи: SUM(amount) по entry_id = 0
```

Баланс счёта — `SELECT SUM(amount) FROM postings WHERE account_id = ?`. Когда проводок миллионы, хранят кэш баланса в отдельной таблице и обновляют его **в той же транзакции**, что и проводку, — а ночью сверяют кэш с суммой проводок.

## Конкурентность: два списания с одного кошелька

У Алии 1 000 ₸, одновременно приходят две оплаты по 800. Если обе прочитают баланс 1 000 и обе пройдут — кошелёк уйдёт в минус. Защиты:

- **блокировка строки счёта** перед проверкой: `SELECT … FROM balances WHERE account_id = ? FOR UPDATE` — вторая транзакция подождёт и увидит уже 200;
- **условный атомарный UPDATE** кэша: `UPDATE balances SET amount = amount - 800 WHERE account_id = ? AND amount >= 800` — 0 строк значит «недостаточно средств»;
- уровень **Serializable** для сложных проверок по нескольким счетам.

## Что это даёт

- **Аудит бесплатно**: любой баланс объясняется списком проводок. «Откуда у клиента минус 30 тенге?» — смотришь проводки.
- **Самопроверка**: сумма проводки ≠ 0 — ошибка в коде, ловится сразу.
- **Отчётность**: обороты за период, баланс на любую дату — простые запросы по журналу.
- **Исправления без потери истории**: сторно вместо `UPDATE`.

<Takeaways>
- Колонка `balance` с `UPDATE` теряет историю. Решение — **леджер с двойной записью** (Пачоли, 1494).
- Проводка: строки дебета и кредита, **сумма = 0**. Журнал **только дописывается**; ошибки — сторно.
- **Баланс считается** из проводок; кэш баланса обновляется в той же транзакции и регулярно сверяется.
- Деньги клиентов — **обязательство** банка, доход — только комиссии.
- Конкурентные списания: `FOR UPDATE`, условный атомарный `UPDATE` или Serializable.
</Takeaways>
