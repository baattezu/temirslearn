В распределённой системе есть ситуация, у которой нет хорошего решения: ты отправил запрос, а ответ не пришёл. Запрос мог **не дойти**. Мог **дойти и выполниться**, а потерялся ответ. Мог выполняться **прямо сейчас**. Снаружи эти случаи неотличимы. Это называют **проблемой двух генералов**, и её нельзя решить в общем виде. Но можно сделать так, чтобы повтор был **безопасным**.

## Как появляются двойные списания

Ретраи есть везде: в HTTP-клиенте, в мобильном приложении при плохой сети, в балансировщике, в очереди сообщений (at-least-once), у пользователя, который дважды жмёт «Оплатить». Если операция не идемпотентна, каждый такой повтор — потенциальное второе списание.

## Идемпотентность

Операция **идемпотентна**, если её повтор даёт тот же результат, что и одно выполнение. `PUT /users/5 {name: "Ада"}` — идемпотентен: сколько ни повторяй, имя будет «Ада». `POST /payments` — нет: каждый вызов создаёт новый платёж.

Решение — **ключ идемпотентности**: клиент генерирует уникальный ключ (UUID) **один раз на намерение** («оплатить этот заказ») и отправляет его во всех повторах. Сервер запоминает ключ вместе с результатом и на повтор отвечает сохранённым результатом, не выполняя операцию снова. Так устроены API Stripe, Adyen и большинства платёжных провайдеров.

## Как сделать на сервере

```sql
CREATE TABLE idempotency_keys (
  key          TEXT PRIMARY KEY,
  request_hash TEXT NOT NULL,          -- чтобы поймать тот же ключ с другим телом
  status       TEXT NOT NULL,          -- in_progress | done
  response     JSONB,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```java
@Transactional
public Response pay(String key, PayRequest req) {
    var existing = keys.tryInsert(key, hash(req));        // INSERT … ON CONFLICT DO NOTHING
    if (existing.isPresent()) {
        var k = existing.get();
        if (!k.requestHash().equals(hash(req))) throw new UnprocessableEntity("ключ уже использован с другим запросом");
        if (k.status() == IN_PROGRESS) throw new Conflict("запрос с этим ключом ещё выполняется");
        return k.response();                              // повтор: тот же ответ
    }
    var result = doPayment(req);                          // бизнес-операция
    keys.complete(key, result);                           // в той же транзакции, что и проводки
    return result;
}
```

Важные детали:

- **Атомарная вставка ключа** (`INSERT … ON CONFLICT`, уникальный индекс) — иначе два одновременных повтора оба решат, что ключа нет.
- **Состояние `in_progress`** — второй параллельный запрос с тем же ключом не должен выполнять операцию; отвечаем 409, клиент повторит позже.
- **Хеш тела запроса** — тот же ключ с другой суммой — ошибка клиента, а не повтор.
- **Результат и бизнес-изменения в одной транзакции** — иначе ключ сохранится, а платёж нет (или наоборот).
- **Срок жизни ключей** — обычно сутки и больше, потом можно чистить.

## Внешние вызовы внутри

Самое трудное место — когда твоя операция сама вызывает внешнего провайдера. Транзакция базы не охватывает сеть: провайдер списал, а твоя транзакция откатилась. Подход:

1. **Записать намерение** до вызова: платёж в статусе `PENDING` с твоим ключом, который **передаётся провайдеру** как его ключ идемпотентности.
2. **Вызвать провайдера.** Повтор с тем же ключом у провайдера тоже безопасен.
3. **Зафиксировать результат.** Таймаут — оставить `PENDING`, а фоновая задача или вебхук провайдера потом выяснят итог.

Так цепочка ключей идёт насквозь: клиент → твой сервис → провайдер, и повтор на любом участке не создаёт второго списания.

## Идемпотентные потребители

То же правило для очередей. Kafka и RabbitMQ доставляют **at-least-once**: сообщение может прийти дважды (консьюмер упал после обработки, но до коммита offset). Потребитель должен быть идемпотентным:

- хранить ID обработанных сообщений (`processed_events` с уникальным ключом) в той же транзакции, что и эффект;
- или делать эффект естественно идемпотентным: `INSERT … ON CONFLICT DO NOTHING`, «установить статус», а не «прибавить».

«Exactly-once» на практике — это **at-least-once доставка + идемпотентная обработка**.

<Takeaways>
- Таймаут ≠ ошибка: запрос мог выполниться, а потерялся ответ. Повторы есть везде — значит, повтор должен быть **безопасным**.
- **Ключ идемпотентности**: один на намерение, во всех повторах; сервер хранит ключ + результат и отвечает тем же.
- Реализация: **атомарная вставка** ключа, состояние **in_progress**, **хеш тела**, ключ и бизнес-изменения в **одной транзакции**.
- Внешние вызовы: записать намерение (`PENDING`) → вызвать провайдера **с тем же ключом** → зафиксировать или выяснить статус позже.
- Очереди: at-least-once + идемпотентный потребитель = практический «exactly-once».
</Takeaways>
