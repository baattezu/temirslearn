Первое, что спрашивают на собесе в финтех: «Какой тип вы используете для денег?» Ответ `double` заканчивает интервью. Почему — проще всего увидеть самому:

## Почему не double

`double` хранит числа в двоичной форме, а десятичные дроби вроде 0.1 в двоичной системе бесконечны — как 1/3 в десятичной. Хранится ближайшее приближение. Для физики это нормально, для денег — нет:

```java
System.out.println(0.1 + 0.2);            // 0.30000000000000004
System.out.println(1.03 - 0.42);          // 0.6100000000000001
double total = 0;
for (int i = 0; i < 10; i++) total += 0.1;
System.out.println(total == 1.0);         // false
```

Каждая такая ошибка крошечная, но они **копятся** в суммах и дают расхождения при сверке, а сравнение через `==` ломает логику.

## Два правильных способа

**1. Целые минорные единицы.** Храни сумму в самых мелких единицах валюты как целое: тиыны, центы. 1 500.75 ₸ → `150075L`. Сложение и сравнение точные и быстрые. Так делают Stripe и многие платёжные API (`amount: 150075`).

Ловушка: **у разных валют разная «копейка»**. Обычно два знака, но у японской иены — ноль, у бахрейнского динара — три. Количество знаков берут из справочника ISO 4217 (`Currency.getDefaultFractionDigits()`), а не зашивают «× 100».

**2. `BigDecimal`.** Десятичное число произвольной точности: значение + масштаб (число знаков после запятой).

```java
BigDecimal price = new BigDecimal("1500.75");      // из строки!
BigDecimal wrong = new BigDecimal(0.1);            // 0.1000000000000000055511151231257827…
BigDecimal ok    = BigDecimal.valueOf(0.1);        // 0.1 — через строковое представление

price.add(new BigDecimal("0.25"));                 // неизменяемый: возвращает новый объект
price.multiply(rate).setScale(2, RoundingMode.HALF_EVEN);
```

Ловушки `BigDecimal`:
- **создавай из строки** или через `valueOf`, не из `double`;
- **`equals` учитывает масштаб**: `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` — `false`. Сравнивай через `compareTo(...) == 0`. Это ломает `HashSet` и ключи в `Map` — нормализуй масштаб;
- **деление** без указания точности бросает исключение на бесконечных дробях: `ONE.divide(THREE)` → `ArithmeticException`. Всегда указывай масштаб и режим округления.

## Деньги — это сумма и валюта

Сумма без валюты — бессмыслица: 100 тенге и 100 долларов складывать нельзя. Поэтому деньги — это **value object**:

```java
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(currency);
        amount = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.UNNECESSARY);
        // UNNECESSARY бросит исключение, если сумма точнее, чем позволяет валюта
    }
    public Money plus(Money o) {
        requireSameCurrency(o);
        return new Money(amount.add(o.amount), currency);
    }
    public boolean isNegative() { return amount.signum() < 0; }
    private void requireSameCurrency(Money o) {
        if (!currency.equals(o.currency)) throw new IllegalArgumentException(currency + " vs " + o.currency);
    }
}
```

Сложить тенге с долларами теперь нельзя даже случайно. Конвертация — отдельная явная операция с курсом, датой курса и правилом округления.

## Округление — это бизнес-правило

Когда считаешь процент, комиссию, налог, курс — появляются доли копейки, и их надо округлить. Как именно — **не выбор программиста**: правило задают договор, тарифы, налоговый кодекс или регулятор. Типичные варианты:

- **HALF_EVEN** (банковское) — половинки к чётному, без систематического перекоса;
- **HALF_UP** — как в школе;
- **DOWN / UP** — в пользу клиента или банка (например, комиссию часто округляют вверх, а начисление процентов — вниз).

И главное: **округляй один раз и в определённый момент** (например, итог строки чека), а не на каждом промежуточном шаге.

## Распределение без потери копеек

Разделить 100.00 на 3 части: 33.33 × 3 = 99.99 — копейка пропала. В финтехе это недопустимо: сумма частей обязана равняться целому. Алгоритм **распределения остатка**: делим нацело, а оставшиеся копейки раздаём по одной первым частям — 33.34 + 33.33 + 33.33. Так делят рассрочки, сплит счёта, распределение комиссий между партнёрами.

<Takeaways>
- **Никогда `double`** для денег: двоичное приближение, ошибки копятся, `==` ломается.
- Два правильных способа: **целые минорные единицы** (`long`) или **`BigDecimal`** — из строки, `compareTo` вместо `equals`, деление с масштабом.
- Число знаков — **по валюте** (ISO 4217): у иены 0, у динара 3.
- **Money = сумма + валюта** как value object; разные валюты не складываются.
- Округление — **бизнес-правило** (договор, регулятор), один раз и в определённый момент. Делёж — с распределением остатка, чтобы сумма частей равнялась целому.
</Takeaways>
