В финтехе есть правило: **твоим данным нельзя верить, пока они не сверены с чужими**. Твой леджер говорит одно, выписка банка — другое, отчёт провайдера — третье. Иногда виноват баг, иногда потерянный вебхук, иногда граница суток. Сверка (reconciliation) — ежедневный процесс, который находит эти расхождения раньше, чем их найдёт клиент или аудитор.

## Почему деньги расходятся

Даже если код идеален, источники расходятся по причинам, которые от тебя не зависят:

| Причина | Пример |
|---|---|
| **время** | ты записал платёж 23:59:58, банк — следующим днём |
| **потерянные уведомления** | вебхук провайдера не дошёл — у провайдера платёж есть, у тебя `PENDING` |
| **комиссии** | провайдер зачислил 48 750 вместо 50 000 — удержал комиссию |
| **частичные операции** | частичный capture, частичный возврат |
| **дубли** | провайдер или банк провёл операцию дважды |
| **курсы валют** | сумма в выписке пересчитана по курсу другого дня |
| **ручные операции** | бухгалтер провёл корректировку в обход системы |
| **баги** | твой код записал не ту сумму или не записал вовсе |

## Как устроена сверка

<ReconcileDiff />

Типичный процесс:

1. **Получить данные** из обоих источников за период: свой леджер и выписка/отчёт контрагента (файл по SFTP, API, выписка в формате банка).
2. **Нормализовать**: одинаковые форматы сумм, валют, дат, часовых поясов.
3. **Сопоставить** записи: сначала по точному ключу (ID транзакции, референс), потом по правилам «сумма + дата ± 1 день + последние цифры карты».
4. **Классифицировать** несовпадения: совпало / разница в сумме / есть только у нас / есть только у них / дубль.
5. **Разобрать**: часть — автоматическими правилами (известные комиссии, сдвиг дат), остальное — в очередь на ручной разбор.
6. **Закрыть период**: расхождение должно быть нулевым или объяснённым.

## Три уровня сверки

- **Внутренняя**: сумма балансов в леджере = 0, кэш балансов = сумма проводок, статусы платежей соответствуют проводкам.
- **С провайдерами**: наши платежи против отчёта PSP/эквайера — каждый ли платёж есть, совпадают ли суммы и комиссии.
- **С банком**: итог по провайдеру против фактического зачисления на расчётный счёт. Провайдер прислал выплату 1 000 000 — из каких платежей она состоит?

## Что важно в коде

**Внешние ссылки на всё.** У каждой твоей операции должен храниться ID у контрагента (ID платежа у провайдера, референс банковского перевода). Без него сопоставление превращается в угадывание по суммам.

**Неизменяемые снимки.** Сохраняй исходные файлы выписок как есть — понадобится разбирать спор через полгода.

**Детерминированность.** Прогон сверки за один день на одних и тех же данных должен давать один и тот же результат — сверку перезапускают.

**Метрики.** Число и сумма несовпадений по дням, возраст неразобранных расхождений. Рост — ранний признак бага или проблем у контрагента.

<Callout kind="tip" title="Сверка как страховка от багов">
Хорошая сверка ловит баги, которые тесты пропустили: потерянный вебхук, гонку при двойном нажатии, неправильное округление. Многие серьёзные инциденты в финтехе обнаруживают не алерты, а утренний отчёт сверки.
</Callout>

<Takeaways>
- Своим данным не верь, пока они **не сверены** с данными контрагентов.
- Причины расхождений: время, потерянные уведомления, комиссии, частичные операции, дубли, курсы, ручные правки, баги.
- Процесс: получить → нормализовать → **сопоставить** (ID, потом правила) → классифицировать → разобрать → закрыть период.
- Уровни: внутренняя, с провайдерами, с банком.
- В коде: **внешние ID** у всех операций, неизменяемые снимки выписок, детерминированные прогоны, метрики расхождений.
</Takeaways>
