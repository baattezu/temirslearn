Rate limiter ограничивает, сколько запросов клиент может сделать за время. Он защищает сервис от перегрузки и злоупотреблений, делит ресурсы честно между клиентами и экономит деньги на платных зависимостях. «Спроектируй rate limiter» — одна из самых частых задач на system design, потому что она маленькая, но затрагивает алгоритмы, распределённое состояние и компромиссы.

## Алгоритмы

Лимит — 5 запросов в секунду. Сравни, как разные алгоритмы обрабатывают одну и ту же нагрузку, особенно всплеск на стыке секунд:

<RateLimiterViz />

| Алгоритм | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Фиксированное окно** | счётчик на каждый интервал (`user:42:2025-03-08T10:15`) | одна операция INCR | двойной всплеск на границе окон |
| **Скользящий лог** | время каждого запроса за последнее окно | точно | память на каждый запрос |
| **Скользящее окно со счётчиками** | текущее окно + взвешенное предыдущее | почти точно, дёшево | приближение |
| **Ведро токенов** | токены копятся со скоростью r до ёмкости b, запрос тратит токен | допускает контролируемый всплеск, дёшево | два параметра настраивать |
| **Дырявое ведро** | очередь, которая обрабатывается с постоянной скоростью | сглаживает нагрузку | задержки, очередь может переполниться |

На практике чаще всего — **ведро токенов**: «в среднем 100 запросов в секунду, кратковременно до 200».

## Где ставить лимитер

- **API-шлюз / балансировщик** (nginx, Envoy, Kong, Cloudflare) — до приложения, дешевле всего отбросить лишнее.
- **Middleware в сервисе** — когда лимит зависит от бизнес-логики (тариф клиента, тип операции).
- **Перед дорогой зависимостью** — ограничить себя, чтобы не получить бан от внешнего API.

## Распределённый лимитер

Серверов несколько — счётчик должен быть общим. Обычно это Redis:

```lua
-- атомарно в Redis (Lua-скрипт выполняется целиком, без гонок)
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens') or ARGV[1])
local last = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3])
tokens = math.min(ARGV[1], tokens + (ARGV[3] - last) * ARGV[2] / 1000)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return allowed and 1 or 0
```

Вопросы, которые стоит обсудить на собесе:
- **Гонки**: «прочитать → проверить → записать» из двух серверов одновременно пропустит лишнее. Нужна атомарность — Lua-скрипт или `INCR` + `EXPIRE`.
- **Задержка**: поход в Redis на каждый запрос — +1 мс. Можно держать локальный лимитер с долей общего лимита и синхронизироваться реже, жертвуя точностью.
- **Отказ Redis**: открыть (пропускать всех) или закрыть (отказывать всем)? Обычно **fail open** — лучше временно без лимита, чем полный отказ сервиса.
- **Ключ**: по пользователю, API-ключу, IP (осторожно с NAT — тысячи людей за одним IP), по эндпоинту.

## Ответ клиенту

- Статус **429 Too Many Requests**.
- Заголовки: `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` — клиент знает, когда повторить.
- Клиенту — повторы с **экспоненциальной задержкой и джиттером**, иначе все отклонённые вернутся одновременно.

<Takeaways>
- Rate limiter защищает от перегрузки, злоупотреблений и счетов от зависимостей.
- Алгоритмы: **фиксированное окно** (просто, всплеск на границе), **скользящий лог/окно** (точнее), **ведро токенов** (стандарт: среднее + контролируемый всплеск), дырявое ведро.
- Распределённо — общий счётчик в Redis с **атомарностью** (Lua), решение про **fail open**, выбор ключа.
- Ответ: **429** + `Retry-After`; клиент — повторы с экспонентой и джиттером.
</Takeaways>
