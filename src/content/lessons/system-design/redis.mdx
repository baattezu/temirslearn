Redis — хранилище структур данных в памяти. Его используют как кэш, хранилище сессий, счётчики, rate limiter, очереди, лидерборды, pub/sub и распределённые блокировки. Сальваторе Санфилиппо написал его в 2009 году, когда его сервис аналитики в реальном времени упёрся в MySQL. Чтобы пользоваться Redis правильно, нужно понимать три вещи: он однопоточный, данные живут в памяти, а у каждой структуры своя сложность операций.

## Один поток

Команды Redis выполняются **по одной в одном потоке** (сетевой ввод-вывод в новых версиях бывает многопоточным, но исполнение — нет). Плюсы: каждая команда атомарна, блокировок нет, всё предсказуемо. Минус: одна медленная команда останавливает **всех** клиентов.

Опасные команды на больших данных: `KEYS *`, `SMEMBERS`/`HGETALL` огромных коллекций, `DEL` большого ключа (в новых версиях есть неблокирующий `UNLINK`), `LRANGE 0 -1`, тяжёлые Lua-скрипты. Вместо `KEYS` — `SCAN` с курсором. Медленные команды показывает `SLOWLOG GET`.

## Структуры и для чего они

| Тип | Операции | Применение |
|---|---|---|
| **String** | `GET`, `SET … EX`, `INCR` | кэш, счётчики, флаги, блокировки (`SET key val NX PX 30000`) |
| **Hash** | `HSET`, `HGET`, `HINCRBY` | объект с полями: профиль, корзина |
| **List** | `LPUSH`, `RPOP`, `BLMOVE` | простые очереди, последние N событий |
| **Set** | `SADD`, `SISMEMBER`, `SINTER` | уникальные посетители, теги, пересечения |
| **Sorted Set** | `ZADD`, `ZRANGE`, `ZRANGEBYSCORE` | лидерборды, очереди с приоритетом, скользящее окно лимитера |
| **Stream** | `XADD`, `XREADGROUP`, `XACK` | журнал событий с группами потребителей (мини-Kafka) |
| **HyperLogLog** | `PFADD`, `PFCOUNT` | приблизительное число уникальных за 12 КБ памяти |

Sorted Set внутри — **skip list** + хеш-таблица: `ZADD` и поиск по рангу за O(log n). Мелкие коллекции Redis хранит в компактном формате (listpack) — экономия памяти в разы.

## Если сервер перезапустится

Данные в памяти, но Redis умеет их сохранять:
- **RDB** — снимок всей базы раз в N минут (форк процесса + copy-on-write). Быстрое восстановление, но потеря данных за последние минуты.
- **AOF** — журнал каждой записи; `appendfsync everysec` — потеря не больше секунды.
- Часто включают оба.

Даже с AOF Redis — не основная база для данных, которые нельзя потерять: репликация асинхронная, и при падении мастера последние записи могут исчезнуть.

## Память и вытеснение

Когда память кончается, срабатывает `maxmemory-policy`:
- `noeviction` — ошибки на запись (для данных, которые нельзя терять);
- `allkeys-lru` / `allkeys-lfu` — вытеснять редко используемые (для кэша);
- `volatile-*` — только ключи с TTL.

LRU в Redis — **приближённый**: берётся случайная выборка ключей и вытесняется худший из них. Точный LRU требовал бы связного списка всех ключей и лишней памяти.

## Масштабирование

- **Репликация**: мастер + реплики для чтения, **Sentinel** следит за мастером и переключает при падении.
- **Redis Cluster**: 16 384 слота, ключ попадает в слот по `CRC16(key) % 16384`, слоты распределены между мастерами. Операции над несколькими ключами работают, только если ключи в одном слоте — для этого есть hash tags: `{user:42}:cart` и `{user:42}:profile` попадут вместе.

## Распределённая блокировка

```
SET lock:order:42 <уникальный-токен> NX PX 30000
-- ... работа ...
-- снять только свою: проверить токен и удалить атомарно (Lua)
```

Подводные камни: процесс может «уснуть» (пауза GC) дольше TTL, блокировку возьмёт другой, а первый проснётся и продолжит. Для корректности нужен **fencing token**, который проверяет само хранилище данных. Для задач, где важна строгая корректность, лучше блокировки в базе (`SELECT … FOR UPDATE`, advisory locks) или etcd.

<Takeaways>
- Redis — структуры данных в памяти: кэш, счётчики, лимитеры, очереди, лидерборды, блокировки.
- **Один поток исполнения**: команды атомарны, но медленная команда (`KEYS`, огромные коллекции) блокирует всех — используй `SCAN`, `UNLINK`, `SLOWLOG`.
- Структуры: String, Hash, List, Set, **Sorted Set** (skip list), Stream, HyperLogLog.
- Персистентность: **RDB** (снимки) и **AOF** (журнал); репликация асинхронная — не основное хранилище критичных данных.
- Вытеснение по `maxmemory-policy` (приближённый LRU/LFU); масштабирование — реплики + Sentinel, Redis Cluster со слотами и hash tags.
- Блокировки через `SET NX PX` + токен; для строгой корректности — fencing token или база/etcd.
</Takeaways>
