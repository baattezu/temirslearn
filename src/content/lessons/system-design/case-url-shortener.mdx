Классическая задача system design: «Спроектируй сервис коротких ссылок вроде bit.ly». Она удобна для разбора: маленькая, но затрагивает генерацию id, хранилище, кэш, нагрузку на чтение и аналитику. Пройдём секцию так, как её стоит вести на собесе — за 45 минут.

## 1. Требования (5 минут)

Сначала вопросы, а не рисование.

**Функциональные:**
- по длинной ссылке выдать короткую;
- переход по короткой — редирект на длинную;
- опционально: свой алиас, срок жизни, статистика переходов.

**Нефункциональные (уточняем у интервьюера):**
- 100 млн новых ссылок в месяц;
- чтений в 100 раз больше, чем записей;
- редирект быстрый (p99 < 50 мс) и почти всегда доступен;
- короткий код — как можно короче, не угадываемый подряд.

## 2. Оценки (5 минут)

<CapacityCalc />

Для наших цифр:
- запись: 100 млн / (30 дней × 86 400 с) ≈ **40 в секунду**, в пике ~200;
- чтение: ×100 → **4 000 в секунду**, в пике ~20 000;
- хранилище: 100 млн × 12 мес × 5 лет = 6 млрд ссылок × ~500 байт ≈ **3 ТБ**.

Вывод: система **читающая**, запись скромная — основная работа в кэше и быстром поиске по ключу.

## 3. API (3 минуты)

```
POST /api/links  { "url": "https://…", "alias": "optional", "ttlDays": 30 }
  → 201 { "code": "aZ3kP9q", "short": "https://sho.rt/aZ3kP9q" }

GET /{code}
  → 301 или 302, Location: https://…
```

**301 или 302?** 301 (постоянный) браузер кэширует — меньше нагрузки, но статистика переходов теряется. 302 — каждый переход проходит через нас. Если нужна аналитика — 302.

## 4. Генерация кода (главный вопрос, 10 минут)

Сколько символов нужно? Base62 (0–9, a–z, A–Z):

<Base62Viz />

7 символов — 3.5 трлн кодов, с запасом на годы. Варианты получения кода:

| Способ | Плюсы | Минусы |
|---|---|---|
| **Хеш URL** (MD5 → первые 7 символов) | одинаковые URL → один код | коллизии: нужна проверка и повтор |
| **Счётчик + base62** | без коллизий, короткие коды | один счётчик — узкое место; коды угадываются подряд |
| **Диапазоны id** (каждый сервер берёт пачку по 10 000 у координатора) | без коллизий, без координации на каждый запрос | при падении сервера дыры в нумерации (не страшно) |
| **Случайный код + проверка** | не угадываются | проверка уникальности на каждой записи, растёт вероятность коллизий |

Хороший ответ: **диапазоны id** + **перемешивание** (биекция id → id, например умножение по модулю или Feistel-шифр), чтобы коды не шли подряд.

## 5. Схема (10 минут)

```
клиент → CDN/балансировщик → сервис ссылок ─┬→ Redis (code → url)  ← 99% чтений
                                             ├→ база (code PK, url, created, expires)
                                             └→ Kafka (события переходов) → аналитика
```

- **Хранилище**: доступ только по ключу, данных терабайты — подходит и шардированный Postgres (шард по `code`), и key-value вроде DynamoDB/Cassandra.
- **Кэш**: популярные ссылки — малая доля всех (закон Парето). Redis с LRU перед базой снимает большинство чтений; горячий ключ можно кэшировать и в памяти сервиса.
- **Аналитика**: не писать в базу на каждый редирект. Событие в Kafka → агрегация батчами → отдельное хранилище (ClickHouse).

## 6. Узкие места и компромиссы (10 минут)

- **Горячая ссылка** (вирусный пост, миллион переходов в минуту): локальный кэш в сервисе + CDN для 301.
- **Злоупотребления**: rate limiting на создание, проверка URL по спискам вредоносных, капча.
- **Свои алиасы**: уникальный индекс; занято — ошибка, а не перезапись.
- **Срок жизни**: TTL в кэше, фоновая очистка в базе.
- **Отказ кэша**: «грохот» в базу — защита от stampede (см. урок про кэширование), circuit breaker.
- **Мультирегион**: редиректы читаются из ближайшего региона; запись в один регион с асинхронной репликацией — новая ссылка может быть недоступна в другом регионе секунду. Обсуди, приемлемо ли это.

<Takeaways>
- Ход секции: **требования → оценки → API → ключевое решение → схема → узкие места**.
- Сокращатель — **читающая** система (×100 чтений): главное — кэш и поиск по ключу.
- 7 символов base62 — 3.5 трлн кодов. Генерация: **диапазоны id + перемешивание**; хеши требуют обработки коллизий.
- **301 против 302**: кэширование против аналитики.
- Аналитика — через очередь, не синхронными записями; горячие ссылки — локальный кэш и CDN.
</Takeaways>
