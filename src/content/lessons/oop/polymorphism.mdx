Полиморфизм — способность одного и того же вызова вести себя по-разному в зависимости от объекта. `shape.area()` для круга считает πr², для квадрата — сторону в квадрате, а вызывающий код один и тот же. Это главный инструмент расширяемости: добавляешь новый класс — старый код работает с ним без изменений.

## Три вида полиморфизма

1. **Подтиповый (динамический)** — то, что обычно имеют в виду в ООП. Метод выбирается **во время выполнения** по реальному классу объекта: `Shape s = new Circle(); s.area()`.
2. **Параметрический** — дженерики: `List<T>` одинаково работает с любым T.
3. **Ad hoc** — перегрузка: `print(int)` и `print(String)` — разные методы с одним именем. Выбирается **при компиляции** по статическим типам аргументов.

Ловушка на собесе: перегрузка выбирается по **объявленному** типу, переопределение — по **реальному**.

```java
class Printer {
    void print(Object o) { System.out.println("object"); }
    void print(String s) { System.out.println("string"); }
}
Object x = "hello";
new Printer().print(x);   // "object" — перегрузка решена при компиляции по типу Object
```

## Как это устроено внутри

Как JVM узнаёт, какой `area()` вызвать, если в переменной `Shape`? У каждого объекта в заголовке есть указатель на его класс, а у класса — **таблица виртуальных методов** (vtable): массив адресов реализаций. У переопределённого метода один и тот же номер слота во всех наследниках. Вызов `area()` — это «возьми класс объекта, возьми слот N из его таблицы, прыгни по адресу». Пройди по шагам:

## JIT убирает цену

HotSpot смотрит, какие классы **на самом деле** приходят в каждое место вызова:

- **Мономорфный** вызов (всегда один класс) — JIT ставит дешёвую проверку класса и **встраивает** тело метода прямо в вызывающий код. Виртуальность исчезает полностью, а после встраивания открываются другие оптимизации.
- **Биморфный** (два класса) — встраиваются оба варианта за проверкой.
- **Мегаморфный** (три и больше) — честный поиск по таблице, без встраивания.

Поэтому в горячих циклах важно, чтобы в одно место кода не приходил «зоопарк» классов. Это одна из причин, почему в высокопроизводительном Java-коде иногда избегают слишком глубоких иерархий.

В современной Java есть и третий путь — **sealed-интерфейс + `switch` с pattern matching**. Он удобнее, когда набор вариантов закрыт и операций над ними много: добавишь вариант — компилятор покажет все места, где его не обработали. Полиморфизм удобнее, когда варианты добавляют часто, а операций мало. Это известная **проблема выражения** (expression problem): нельзя одинаково легко добавлять и типы, и операции.

<Takeaways>
- Полиморфизм бывает **подтиповый** (по реальному классу в рантайме), **параметрический** (дженерики) и **ad hoc** (перегрузка по объявленному типу при компиляции).
- Виртуальный вызов: объект → класс → **vtable** → слот → адрес метода.
- **JIT** встраивает мономорфные и биморфные вызовы; дорого только в мегаморфном случае.
- Главная польза — **заменить ветвления по типу**: новый вариант — новый класс, старый код не меняется.
- Альтернатива — **sealed + pattern matching**: удобнее, когда типы закрыты, а операций много (проблема выражения).
</Takeaways>
