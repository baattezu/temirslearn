Самое частое заблуждение об инкапсуляции: «сделал поля `private`, сгенерировал геттеры и сеттеры — инкапсулировал». Нет. Если у каждого поля есть публичный сеттер, объект защищён ровно так же, как с публичными полями. Инкапсуляция — не про модификатор доступа, а про **инварианты**.

## Инвариант — правило, которое всегда истинно

Инвариант — условие, которое верно для объекта в любой момент, когда кто-то на него смотрит:

- баланс счёта не ниже кредитного лимита;
- в заказе есть хотя бы одна позиция, а итог равен сумме позиций;
- дата окончания бронирования позже даты начала;
- у оплаченного заказа есть номер платежа.

Задача объекта — **сделать нарушение инварианта невозможным**. Если правило может нарушить любой код в проекте, оно не правило, а пожелание. Попробуй сломать счёт в двух версиях:

## Как не дать утечь внутренностям

**Не отдавай изменяемое состояние наружу.** Геттер, возвращающий внутренний список, — дыра: `order.getLines().clear()` обходит все проверки. Отдавай копию (`List.copyOf`) или неизменяемое представление.

**Делай объекты неизменяемыми, где можно.** У неизменяемого объекта инвариант проверяется **один раз — в конструкторе**, и дальше нарушиться не может. `record` с проверкой в компактном конструкторе — идеальный инструмент:

```java
record DateRange(LocalDate from, LocalDate to) {
    DateRange {
        if (!to.isAfter(from)) throw new IllegalArgumentException(from + " .. " + to);
    }
    long nights() { return DAYS.between(from, to); }
}
```

**«Говори, а не спрашивай» (Tell, Don't Ask).** Вместо того чтобы спросить у объекта данные и принять решение снаружи — попроси объект сделать дело:

```java
// спрашиваем и решаем за объект
if (account.getBalance().compareTo(amount) >= 0 && !account.isBlocked()) {
    account.setBalance(account.getBalance().subtract(amount));
}
// говорим, что сделать
account.withdraw(amount);
```

**Закон Деметры** — «разговаривай только с ближайшими друзьями»: `order.customer().address().city()` знает устройство трёх объектов. Лучше `order.deliveryCity()`.

## Где граница разумного

Инкапсуляция — не значит «прятать всё». DTO для API, записи для передачи данных между слоями — честные структуры без поведения, и `record` для них идеален. Богатая модель нужна там, где есть **правила**. Нет правил — нет и инвариантов, которые нужно охранять.

<Takeaways>
- Инкапсуляция — это **защита инвариантов**, а не `private` + геттеры и сеттеры.
- **Богатая модель**: правила живут в объекте, нарушить их снаружи нельзя. Анемичная — правила в сервисах, их легко обойти.
- Не отдавай изменяемое состояние наружу (копии), предпочитай **неизменяемые объекты** — инвариант проверяется один раз в конструкторе.
- **Tell, Don't Ask** и **закон Деметры** — проси объект сделать дело, не лезь в его устройство.
- DTO и записи без правил — нормальны; богатая модель нужна там, где есть правила.
</Takeaways>
