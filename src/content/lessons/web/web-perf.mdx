Скорость страницы — это не одно число. Google измеряет её тремя метриками **Core Web Vitals**, и они влияют и на поиск, и на конверсию. Каждая отвечает на свой вопрос пользователя: «грузится?», «реагирует?», «не прыгает?».

## Три метрики

| Метрика | Вопрос | Хорошо |
|---|---|---|
| **LCP** (Largest Contentful Paint) | когда отрисовался самый большой видимый элемент (обычно главная картинка или заголовок) | ≤ 2.5 с |
| **INP** (Interaction to Next Paint) | сколько проходит от клика/нажатия до следующего кадра | ≤ 200 мс |
| **CLS** (Cumulative Layout Shift) | насколько контент неожиданно сдвигается | ≤ 0.1 |

Считаются по **75-му перцентилю** реальных пользователей (данные Chrome UX Report), а не по запуску Lighthouse на быстром ноутбуке.

## LCP: что тормозит загрузку

<WebVitals />

Цепочка, которую разбирают при плохом LCP:

1. **TTFB** — сервер медленно отдаёт HTML (нет кэша, нет CDN, тяжёлый SSR).
2. **Блокирующие ресурсы** — CSS в `<head>` блокирует отрисовку, `<script>` без `defer`/`async` — парсинг.
3. **Позднее обнаружение** — главная картинка подгружается из CSS или JS, и браузер узнаёт о ней поздно. Лечится `<link rel="preload">` или `fetchpriority="high"` на `<img>`.
4. **Тяжёлый ресурс** — картинка 3 МБ вместо AVIF/WebP нужного размера (`srcset`).
5. **Клиентский рендеринг** — пока не загрузится и не выполнится весь JS-бандл, отображать нечего. SSR/SSG/стриминг отдают готовый HTML.

## INP: отзывчивость

INP плох, когда главный поток занят (см. урок про event loop): тяжёлый обработчик, долгий рендер React, сторонние скрипты аналитики. Лечение — разбивать работу (`scheduler.yield()`), переносить в Web Worker, уменьшать JS, виртуализировать длинные списки, откладывать некритичное (`requestIdleCallback`).

## CLS: прыжки вёрстки

- картинки и видео без `width`/`height` (или `aspect-ratio`) — место не зарезервировано;
- реклама, баннеры, встраиваемые виджеты, появляющиеся сверху;
- веб-шрифты, отличающиеся метриками от запасного (`font-display: optional`, `size-adjust`);
- контент, вставляемый над уже видимым после загрузки данных — резервируй место скелетоном.

<Callout kind="tip" title="Бюджет JS">
Самая частая причина всех трёх проблем на современных сайтах — слишком много JavaScript. Каждые 100 КБ сжатого JS — это не только загрузка, но и парсинг и выполнение на слабом телефоне. Разделение кода по маршрутам (`lazy`), удаление неиспользуемых зависимостей и анализ бандла (`vite-bundle-visualizer`) часто дают больше, чем любые микрооптимизации. temirslearn так и устроен: тяжёлые страницы (редактор кода, уроки) — отдельными чанками.
</Callout>

<Takeaways>
- **LCP** (загрузка, ≤ 2.5 с), **INP** (отзывчивость, ≤ 200 мс), **CLS** (стабильность, ≤ 0.1) — по p75 реальных пользователей.
- LCP: TTFB, блокирующие CSS/JS, позднее обнаружение главной картинки (preload, fetchpriority), её размер, клиентский рендеринг.
- INP: длинные задачи главного потока → дробить, воркеры, меньше JS.
- CLS: размеры у медиа, резерв места, шрифты.
- Главный рычаг — **меньше JavaScript**.
</Takeaways>
