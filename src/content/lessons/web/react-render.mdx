React описывает интерфейс как функцию от состояния: `UI = f(state)`. Когда состояние меняется, React вызывает функцию компонента заново, сравнивает результат с предыдущим и применяет к DOM только разницу. Понимание того, **когда** и **что** перерисовывается, — главное для производительности и отсутствия странных багов.

## Рендер и коммит

1. **Триггер**: `setState`, изменение контекста, перерисовка родителя.
2. **Рендер**: React вызывает функции компонентов и получает новое дерево элементов (виртуальный DOM). Это чистые вычисления, без побочных эффектов.
3. **Сравнение** (reconciliation): новое дерево против старого.
4. **Коммит**: минимальные изменения в реальном DOM, затем эффекты (`useLayoutEffect` синхронно, `useEffect` после отрисовки).

«Перерисовался» компонент — значит, вызвана его функция. Это ещё не значит, что изменился DOM.

## Кто перерисовывается

Правило по умолчанию: **компонент, чьё состояние изменилось, и все его потомки** — независимо от того, поменялись ли их пропсы.

<ReactRerender />

- `React.memo(Component)` пропускает рендер, если пропсы **поверхностно** равны прошлым.
- Функции и объекты, созданные в теле компонента, — **новые** на каждом рендере. Поэтому `onSelect={() => …}` ломает memo у ребёнка. `useCallback` и `useMemo` сохраняют ссылку между рендерами.
- Начиная с React 19, **React Compiler** расставляет мемоизацию автоматически — ручные `useMemo`/`useCallback` становятся нужны реже.

Не мемоизируй всё подряд: сравнение пропсов тоже стоит. Сначала профилировщик (React DevTools → Profiler), потом оптимизация.

## Reconciliation и ключи

Сравнивая деревья, React исходит из двух эвристик:

- элемент другого **типа** на том же месте — поддерево пересоздаётся целиком (состояние теряется);
- элементы списка сопоставляются по **`key`**.

Ключ — идентичность элемента между рендерами. `key={index}` ломается при вставке и сортировке: состояние (текст в инпуте, раскрытость) «переезжает» к соседнему элементу. Ключ должен быть стабильным id из данных. А смена `key` у компонента — штатный способ **сбросить** его состояние.

## Состояние и батчинг

- `setState` не меняет значение сразу — он планирует новый рендер. В текущем вызове функции `count` остаётся старым.
- Несколько `setState` в одном обработчике (а с React 18 — и в промисах, таймерах) **батчатся** в один рендер.
- Если новое значение зависит от старого — функциональная форма: `setCount(c => c + 1)`.

<Takeaways>
- Рендер = вызов функции компонента; коммит = изменение DOM только там, где есть разница.
- По умолчанию перерисовываются компонент с новым состоянием **и все потомки**.
- `memo` сравнивает пропсы поверхностно; новые функции и объекты ломают его → `useCallback`/`useMemo` (или React Compiler).
- `key` — идентичность в списках; индекс как ключ ломает состояние при перестановках.
- `setState` асинхронен и батчится; зависимое обновление — функциональной формой.
</Takeaways>
