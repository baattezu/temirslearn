Spring появился в 2003 году как протест. Тогдашний стандарт корпоративной Java — EJB 2 — требовал на каждый сервис по три интерфейса, XML-дескрипторы и тяжёлый сервер приложений; тесты без сервера не запускались. Род Джонсон в книге «Expert One-on-One J2EE Design and Development» показал, что всё то же можно делать на **обычных Java-объектах** (POJO), если отдать их создание и связывание контейнеру. Из примеров к книге вырос Spring Framework — и через несколько лет вытеснил EJB.

## IoC-контейнер: кто создаёт объекты

Без Spring объекты создают друг друга сами: `new OrderService(new JdbcOrderRepository(dataSource), new StripeGateway(key))`. С ростом приложения граф из сотен объектов собирать руками тяжело, а подменить зависимость в тесте — ещё тяжелее.

**Инверсия управления**: объекты не создают зависимости, а получают их. Создаёт и связывает их **контейнер** (`ApplicationContext`). Объекты, которыми он управляет, называются **бинами**.

```java
@Service
public class OrderService {
    private final OrderRepository orders;
    private final PaymentGateway payments;

    public OrderService(OrderRepository orders, PaymentGateway payments) {   // единственный конструктор — @Autowired не нужен
        this.orders = orders;
        this.payments = payments;
    }
}

@Configuration
class PaymentConfig {
    @Bean
    PaymentGateway paymentGateway(@Value("${stripe.key}") String key) {
        return new StripeGateway(key);           // свой код создания — для чужих классов
    }
}
```

Откуда контейнер знает о бинах: **сканирование** классов с `@Component` и его разновидностями (`@Service`, `@Repository`, `@Controller`) и методы `@Bean` в классах `@Configuration`.

Самое важное здесь — шаг 7. **Почти вся «магия» Spring — это прокси**, созданные пост-процессорами: `@Transactional`, `@Async`, `@Cacheable`, `@Retryable`, method security, AOP. В контекст кладётся обёртка, и все вызовы снаружи идут через неё.

Отсюда классические грабли:
- **вызов изнутри класса** (`this.method()`) идёт мимо прокси — аннотации не работают;
- **`final`-классы и методы** CGLIB не может переопределить — прокси не сработает;
- **`private`-методы** не проксируются вообще.

## Scope: сколько экземпляров

| Scope | Экземпляров | Когда |
|---|---|---|
| `singleton` (по умолчанию) | один на контекст | сервисы, репозитории — 95% бинов |
| `prototype` | новый при каждом запросе бина | изменяемые объекты с состоянием |
| `request` / `session` | на HTTP-запрос / сессию | данные текущего пользователя в веб-приложении |

Раз бины-синглтоны общие для всех потоков, **в них не должно быть изменяемого состояния**, связанного с запросом. Поле `currentUser` в `@Service` — гарантированная гонка между запросами.

Ловушка: если внедрить prototype-бин в singleton, он создастся **один раз** — при создании синглтона. Нужен `ObjectProvider<T>` и `getObject()` при каждом использовании.

## AOP: сквозная функциональность

Логирование, метрики, транзакции, безопасность нужны в сотнях методов. **Аспектно-ориентированное программирование** описывает такую логику один раз и применяет её по правилу:

```java
@Aspect @Component
class TimingAspect {
    @Around("@annotation(Timed)")
    Object time(ProceedingJoinPoint jp) throws Throwable {
        long t = System.nanoTime();
        try { return jp.proceed(); }                 // вызов настоящего метода
        finally { metrics.record(jp.getSignature().getName(), System.nanoTime() - t); }
    }
}
```

Под капотом — тот же прокси вокруг бина.

## Циклические зависимости

`A` зависит от `B`, `B` — от `A`. При внедрении через конструкторы Spring падает при старте — и это хорошо: цикл почти всегда признак неудачного разделения ответственности. С Spring Boot 2.6 циклы запрещены и через поля. Лечится выносом общей части в третий бин или событием вместо прямого вызова.

<Takeaways>
- Spring (Род Джонсон, 2003) — ответ тяжёлому EJB: обычные объекты + контейнер, который их создаёт и связывает (**IoC**, внедрение зависимостей).
- Бины находятся сканированием (`@Component`, `@Service`…) и методами `@Bean`; внедрение — через конструктор.
- Жизненный цикл: описание → создание → зависимости → `@PostConstruct` → **пост-процессоры и прокси** → использование → `@PreDestroy`.
- Почти вся магия — **прокси**: отсюда грабли с `this.method()`, `final` и `private`.
- Синглтоны общие для потоков — без состояния запроса. Prototype в singleton — через `ObjectProvider`. Циклы зависимостей — признак плохого дизайна.
</Takeaways>
