«Расскажи про память JVM» — один из самых частых вопросов на Java-собесе. Хороший ответ — это не список областей, а понимание: что где лежит, сколько это стоит в байтах и почему это влияет на GC и скорость.

## Области памяти

| Область | Что там | Чья | Ошибка при переполнении |
|---|---|---|---|
| **Heap** | все объекты и массивы | общая для потоков | `OutOfMemoryError: Java heap space` |
| **Stack** потока | кадры методов: локальные переменные, операнды | у каждого потока своя | `StackOverflowError` |
| **Metaspace** | классы, методы, байткод, константы | общая, нативная память | `OutOfMemoryError: Metaspace` |
| **Code cache** | машинный код от JIT | общая | JIT отключается, всё медленнее |
| **Direct memory** | `ByteBuffer.allocateDirect`, Netty | нативная | `OutOfMemoryError: Direct buffer memory` |

Размер heap задаётся `-Xms`/`-Xmx`, стека потока — `-Xss` (по умолчанию ~1 МБ). Важная деталь для контейнеров: **память процесса больше, чем `-Xmx`**. К heap добавляются metaspace, стеки всех потоков, code cache, direct buffers и сам GC. Поэтому при лимите контейнера 2 ГБ и `-Xmx2g` процесс убьёт OOM killer. Используй `-XX:MaxRAMPercentage=75`.

## Стек и куча в работе

Пройди программу по шагам и следи, что попадает в кадр стека, а что — в кучу:

Что вынести:

- **Примитивы** локальных переменных лежат в кадре стека, **объекты** — всегда в куче, в кадре только ссылка.
- Java передаёт аргументы **по значению**. Для объекта значение — это ссылка: метод может изменить объект, но не может заменить его у вызывающего.
- Снятие кадра — O(1) и мгновенно. Объекты в куче освобождает только GC, и только когда они **недостижимы от корней**: стеков потоков, static-полей, JNI-ссылок. Подсчёта ссылок нет, поэтому циклы не мешают.

<Callout kind="info" title="Escape analysis">
Если JIT доказал, что объект не «убегает» из метода (не возвращается, не сохраняется в поле, не передаётся наружу), он может вообще не создавать его в куче — разложить поля по регистрам (**scalar replacement**). Поэтому короткоживущие итераторы и временные объекты в горячем коде часто бесплатны. Но это оптимизация C2, а не гарантия.
</Callout>

## Сколько весит объект

У каждого объекта в HotSpot есть **заголовок**:

- **mark word** (8 Б): identity hash, возраст для GC, состояние блокировки;
- **указатель на класс** (4 Б при compressed class pointers, иначе 8);
- у массивов — ещё **длина** (4 Б).

Дальше идут поля, а весь объект выравнивается до 8 байт. Выбери класс:

**Compressed oops**: при heap меньше ~32 ГБ ссылки хранятся как 32-битные смещения (умноженные на 8 — отсюда и предел 32 ГБ). Это экономит память и кэш. Поэтому heap 31 ГБ часто вмещает **больше** объектов, чем 33 ГБ.

Практические выводы:

- `List<Integer>` на миллион элементов — это ~16 МБ на объекты `Integer` + ~4 МБ на массив ссылок, против ~4 МБ у `int[]`. Для больших коллекций примитивов — `int[]`, `IntStream` или библиотеки вроде fastutil.
- `Integer` от −128 до 127 кэшируются (`Integer.valueOf`), поэтому `==` для них «работает», а для 1000 — уже нет. Сравнивай через `equals`.
- В Java 25+ появились компактные заголовки (`-XX:+UseCompactObjectHeaders`, JEP 519): заголовок 8 байт вместо 12, и мелкие объекты становятся на 10–20% легче.

<Takeaways>
- **Heap** — объекты (общий), **stack** — кадры методов с примитивами и ссылками (у каждого потока свой), **metaspace** — классы.
- Память процесса > `-Xmx`: стеки, metaspace, code cache, direct buffers. В контейнере — `MaxRAMPercentage`.
- Передача **по значению**; для объектов копируется ссылка.
- GC собирает **недостижимые от корней** объекты, циклы не проблема.
- Объект = заголовок 12 Б (mark word + klass) + поля, выравнивание до 8. `new Object()` = 16 Б, `Integer` = 16 Б.
- **Compressed oops** до ~32 ГБ heap; escape analysis может убрать аллокацию совсем.
</Takeaways>
