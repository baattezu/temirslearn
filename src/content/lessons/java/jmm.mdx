Java Memory Model (JMM) отвечает на вопрос: **когда запись одного потока гарантированно видна другому?** Без этого невозможно объяснить, почему нужен `volatile`, почему double-checked locking был сломан и почему «у меня работает» в многопоточном коде ничего не значит.

## Почему это вообще проблема

Компилятор, JIT и процессор переставляют операции, если в **одном потоке** результат не меняется:

- JIT выносит чтение поля из цикла (`while (!stop) {}` превращается в `if (!stop) while (true) {}`);
- у каждого ядра есть **store buffer**: запись сначала попадает туда и становится видна другим ядрам позже;
- ARM и другие «слабые» процессоры переставляют даже чтения и записи в разные адреса.

## Классический пример

Два потока, `x = y = 0`. Может ли получиться `r1 = 0` и `r2 = 0`?

<Litmus />

Если перебрать все последовательные чередования, 00 не выходит никогда. Но реальная программа не обязана вести себя как одно из чередований. На x86 запись `x = 1` может ещё сидеть в store buffer, когда поток уже прочитал `y`. Поэтому без синхронизации 00 — допустимый и реально наблюдаемый исход.

## Happens-before

JMM не описывает кэши и барьеры. Она вводит отношение **happens-before** (HB): если запись HB чтение, чтение обязано её увидеть. HB возникает из:

1. **Порядка в программе** внутри одного потока.
2. **Монитора**: `unlock` HB каждого последующего `lock` того же монитора (`synchronized`, `Lock`).
3. **volatile**: запись в volatile-поле HB каждого последующего чтения этого поля.
4. **Thread.start()** HB всех действий нового потока; все действия потока HB успешного `join()`.
5. Транзитивности: если A HB B и B HB C, то A HB C.

Отсюда главный приём — **безопасная публикация**:

```java
class Holder {
    private Config config;              // обычное поле
    private volatile boolean ready;     // флаг публикации

    void publish() {                    // поток A
        config = load();                // 1. обычная запись
        ready = true;                   // 2. volatile-запись
    }
    void use() {                        // поток B
        if (ready) {                    // 3. volatile-чтение увидело true
            config.get();               // 4. гарантированно видит config из шага 1
        }
    }
}
```

1 HB 2 (порядок в потоке), 2 HB 3 (volatile), 3 HB 4 (порядок) — значит 1 HB 4.

## volatile — это не атомарность

`volatile` даёт **видимость и порядок**, но не атомарность составных операций. `count++` на volatile-поле — это чтение, сложение и запись; два потока могут прочитать одно значение и потерять инкремент. Нужны `AtomicInteger.incrementAndGet()` (CAS), `LongAdder` под высокой конкуренцией или блокировка.

## Double-checked locking

```java
private static volatile Singleton instance;   // без volatile — сломано
static Singleton get() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}
```

Без `volatile` ссылка на объект может стать видна другому потоку **раньше**, чем завершился конструктор (запись полей и запись ссылки переставлены). Второй поток увидит не-null и полуинициализированный объект. Проще — holder-класс: `static class H { static final Singleton I = new Singleton(); }`. Инициализация класса потокобезопасна по спецификации.

<Callout kind="tip" title="final-поля">
У `final`-полей отдельная гарантия: если ссылка на объект не «утекла» из конструктора, любой поток, получивший ссылку, увидит final-поля полностью инициализированными — даже без синхронизации. Поэтому неизменяемые объекты (records, String) можно безопасно передавать между потоками.
</Callout>

<Takeaways>
- Без синхронизации JIT и CPU **переставляют** операции и держат записи в store buffer → другой поток может их не увидеть.
- JMM гарантирует видимость только через **happens-before**: порядок в потоке, мониторы, volatile, start/join, транзитивность.
- **volatile** = видимость + запрет перестановок, но **не атомарность** (`count++` ломается) → `Atomic*`, `LongAdder`, lock.
- Безопасная публикация: volatile, final-поля, synchronized, потокобезопасные коллекции.
- Double-checked locking требует `volatile` или holder-класс.
</Takeaways>
