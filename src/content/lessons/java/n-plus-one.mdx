Самая частая проблема производительности в приложениях на ORM — и самая частая тема вопросов о Hibernate на собесе. Страница со списком из 100 заказов делает 101 запрос в базу. На локальной машине с базой рядом это 30 мс, и никто не замечает. В проде, где каждый запрос — сетевой round-trip, это секунды.

## Откуда берётся N+1

```java
List<Order> orders = orderRepository.findAll();      // 1 запрос: SELECT * FROM orders
for (Order o : orders) {
    o.getCustomer().getName();                        // + N запросов: SELECT * FROM customers WHERE id = ?
}
```

Связь `customer` ленивая: вместо объекта Hibernate положил прокси, который сходит в базу при первом обращении. Для каждого заказа — свой запрос. Код выглядит невинно, и N+1 часто прячется в маппере DTO, в `toString()` или в шаблоне, который рендерит ответ (если включён `open-in-view`).

## Как лечить

**1. JOIN FETCH в запросе** — загрузить связь тем же запросом:

```java
@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findWithCustomer(@Param("s") Status s);
```

**2. @EntityGraph** — то же, но декларативно, без переписывания запроса:

```java
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(Status s);
```

**3. Пакетная загрузка** — `hibernate.default_batch_fetch_size=50` (или `@BatchSize`): ленивые связи догружаются пачками `WHERE id IN (…)`. Один параметр в конфиге превращает N+1 в 1 + N/50 запросов во всём приложении — хорошая настройка по умолчанию.

**4. DTO-проекция** — если нужны только несколько полей, не грузи сущности вовсе:

```java
@Query("select new com.shop.OrderRow(o.id, o.total, c.name) from Order o join o.customer c")
List<OrderRow> rows();
```

## Ловушки при лечении

- **JOIN FETCH двух коллекций** (`items` и `payments`) → декартово произведение: 100 позиций × 10 платежей = 1000 строк на заказ. Hibernate для двух `List` бросит `MultipleBagFetchException`. Грузи коллекции отдельными запросами или пакетно.
- **JOIN FETCH коллекции + пагинация** → Hibernate не может применить `LIMIT` к строкам JOIN, тянет всё в память и пишет предупреждение HHH90003004. Решение: сначала страница id, потом второй запрос с fetch по этим id.
- **EAGER не лечит N+1** — он лишь делает загрузку обязательной, а в JPQL-запросах связи всё равно догружаются отдельными запросами.

## Как заметить N+1 до прода

- Логи SQL в dev: `spring.jpa.show-sql` или лучше `logging.level.org.hibernate.SQL=debug` — видно, сколько запросов на одну операцию.
- Статистика Hibernate: `hibernate.generate_statistics=true`.
- **Тест на число запросов**: библиотеки вроде datasource-proxy позволяют написать `assertSelectCount(2)` — регрессия N+1 сломает тест.
- В проде — трейсинг (OpenTelemetry): N+1 виден как «лесенка» из одинаковых коротких запросов внутри одного HTTP-запроса.

<Takeaways>
- **N+1**: 1 запрос за список + по запросу на каждый элемент при обращении к ленивой связи. Незаметно локально, больно в проде.
- Лечение: **JOIN FETCH**, **@EntityGraph**, **batch fetch** (`default_batch_fetch_size` — хорошее умолчание), **DTO-проекции**.
- Ловушки: две коллекции в JOIN → декартово произведение; fetch коллекции + пагинация → в памяти; EAGER не лечит.
- Ловить заранее: логи SQL, статистика Hibernate, тесты на число запросов, трейсинг.
</Takeaways>
