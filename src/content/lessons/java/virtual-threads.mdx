Типичный бэкенд большую часть времени **ждёт**: ответа базы, другого сервиса, Kafka. Классическая модель «поток на запрос» тратит поток ОС на всё время ожидания. Потоков ОС тысячи, не миллионы, — и сервис упирается в их число, хотя процессор свободен. Двадцать лет индустрия лечила это реактивным программированием (WebFlux, RxJava): быстро, но код превращается в цепочки колбэков, а стектрейсы — в кашу. Java 21 предложила другой выход — **виртуальные потоки** (Project Loom).

## Как это устроено

Виртуальный поток — объект JVM, а не поток ОС. Его стек хранится в куче и растёт по мере надобности. JVM запускает виртуальные потоки на небольшом пуле **потоков-носителей** (carrier threads, по числу ядер). Когда виртуальный поток доходит до блокирующей операции — чтения из сокета, `sleep`, ожидания блокировки, — JVM **размонтирует** его: сохраняет стек и отдаёт носитель следующему. Когда данные пришли — монтирует обратно, возможно, на другой носитель.

Для твоего кода ничего не меняется: тот же блокирующий стиль, те же `try/catch`, понятные стектрейсы, отладчик работает. Создать можно миллионы.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var id : ids) executor.submit(() -> process(id));   // поток на задачу — и это нормально
}

Thread.ofVirtual().start(() -> handle(request));
```

В Spring Boot 3.2+ — одна настройка: `spring.threads.virtual.enabled=true`, и Tomcat обрабатывает каждый запрос в виртуальном потоке.

## Чего не делать с виртуальными потоками

**Не объединять в пулы.** Виртуальный поток дешёвый, его создают на задачу и выбрасывают. Пул виртуальных потоков — бессмыслица.

**Не ограничивать параллелизм размером пула.** Раньше пул из 50 потоков заодно защищал базу от 51-го одновременного запроса. Теперь потоков сколько угодно — и база получит 10 000 соединений. Ограничивай явно: `Semaphore`, размер пула соединений к БД, rate limiter.

**Осторожно с pinning.** Если виртуальный поток блокируется, будучи «прибитым» к носителю, носитель тоже стоит. До Java 24 так было внутри `synchronized`; JEP 491 в Java 24 это исправил. Остались нативные вызовы (JNI) и некоторые старые драйверы. Диагностика: `-Djdk.tracePinnedThreads=full` в старых версиях, события JFR `jdk.VirtualThreadPinned`.

**Осторожно с ThreadLocal.** Миллион потоков × тяжёлый кэш в ThreadLocal = миллион копий. Для передачи контекста есть **ScopedValue** (финализирован в Java 25).

## Когда что брать

| Нагрузка | Решение |
|---|---|
| много ожидания I/O (типичный REST-сервис, БД, HTTP-вызовы) | **виртуальные потоки** |
| тяжёлые вычисления на CPU | обычный пул размером с число ядер (`ForkJoinPool`, параллельные стримы) |
| потоковая обработка с backpressure, уже написанная на Reactor | реактивщина остаётся уместной |

Виртуальные потоки не делают код быстрее — они дают **больше одновременных ожиданий** при том же числе потоков ОС. Если сервис упирается в CPU или базу, они не помогут.

## Structured concurrency

Ещё одна часть Loom (в Java 25 — превью): параллельные подзадачи с общим временем жизни.

```java
try (var scope = StructuredTaskScope.open()) {
    var user = scope.fork(() -> users.get(id));
    var orders = scope.fork(() -> orders.list(id));
    scope.join();                                  // ждём обе; если одна упала — вторую отменят
    return new Profile(user.get(), orders.get());
}
```

Та же идея, что у корутин Kotlin: подзадачи не переживают свой блок, ошибки и отмена распространяются автоматически.

<Takeaways>
- Бэкенд в основном **ждёт**; «поток ОС на запрос» упирается в число потоков. Реактивщина решала это ценой сложности кода.
- **Виртуальные потоки** (Java 21): объекты JVM на нескольких носителях; при блокирующем I/O поток **размонтируется**. Код остаётся обычным блокирующим.
- Spring Boot 3.2+: `spring.threads.virtual.enabled=true`.
- Не пулить; ограничивать параллелизм явно; следить за **pinning** (исправлен для `synchronized` в Java 24) и ThreadLocal (→ ScopedValue).
- Помогают I/O-нагрузке, не CPU. **Structured concurrency** — подзадачи с общим временем жизни.
