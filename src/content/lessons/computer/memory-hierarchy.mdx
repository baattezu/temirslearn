Почему обход массива в разы быстрее обхода связного списка, хотя оба — O(n)? Почему N+1 запросов к базе убивают страницу, а N+1 обращений к хешмапе — нет? Ответ один: **задержки разных уровней памяти отличаются на порядки**, и O-нотация этого не видит.

## Что стоит запомнить

Точные цифры знать не нужно, нужно знать **порядки**:

- кэши — единицы и десятки наносекунд;
- RAM — около 100 нс, это в ~100 раз медленнее L1;
- SSD — десятки микросекунд, в ~500 раз медленнее RAM;
- сеть внутри датацентра — сотни микросекунд;
- сеть между континентами — десятки и сотни миллисекунд.

Переключи виджет в режим «1 нс = 1 секунда». Если L1 — это секунда, то сходить в RAM — полторы минуты, прочитать с SSD — полдня, а запрос в другой датацентр за океаном — несколько лет.

## Кэш-линии и локальность

Процессор читает память не байтами, а **кэш-линиями по 64 байта**. Прочитал `a[0]` — в кэш заодно попали `a[1]…a[15]` (для int32). А аппаратный **префетчер** замечает, что ты идёшь по адресам подряд, и подтягивает следующие линии заранее.

- **Массив**: элементы лежат подряд → почти каждое обращение попадает в L1.
- **Связный список**: каждый узел где-то в куче → каждое обращение может стоить промах в RAM, ~100 нс.

```java
// одинаковая асимптотика, разная скорость в разы
long sum = 0;
for (int x : array) sum += x;          // последовательно, префетчер доволен
for (Node n = head; n != null; n = n.next) sum += n.value;   // прыжки по куче
```

Ровно поэтому `ArrayList` почти всегда обгоняет `LinkedList`, даже на вставках в середину: сдвиг соседних элементов — дешёвый `memmove` по горячему кэшу.

<Callout kind="tip">
Сильный ответ на вопрос «почему X быстрее Y» почти всегда упирается в одну из этих строк: «это попадание в кэш, а это поход в RAM», «это один round-trip, а это N», «это последовательное чтение, а это случайное».
</Callout>

## Тот же принцип выше по стеку

Иерархия повторяется на каждом уровне системы:

| Уровень | Быстро | Медленно | Как называется приём |
|---|---|---|---|
| CPU | L1/L2 | RAM | локальность данных |
| ОС | page cache | диск | буферизация, readahead |
| База | shared_buffers | диск | индексы, кэш страниц |
| Сервис | Redis/локальный кэш | БД | кэширование |
| Сеть | один batch-запрос | N запросов | батчинг, устранение N+1 |

Твой кейс «42 HTTP-запроса → 1» из этой же таблицы: убрал 41 round-trip.

<Takeaways>
- Знай **порядки**: L1 ~1 нс, RAM ~100 нс, SSD ~50 мкс, датацентр ~0.25 мс, континент ~100 мс.
- Память читается кэш-линиями по 64 Б. Последовательный доступ + префетчер = массивы быстрые, указатели медленные.
- Та же иерархия на каждом уровне: page cache, буферы БД, Redis, батчинг сетевых запросов.
- O-нотация считает операции, а не их стоимость. Константа «100 нс против 1 нс» — это и есть разница в скорости.
</Takeaways>
