Термин «запах кода» придумал Кент Бек, а Мартин Фаулер сделал из него каталог в книге «Рефакторинг» (1999). Запах — не баг: код работает. Это **признак**, что дальше будет больно — менять, тестировать, разбираться. Опытный разработчик чувствует такие места с первого взгляда. Потренируйся:

## Самые частые запахи

| Запах | Как выглядит | Чем грозит | Рефакторинг |
|---|---|---|---|
| **Длинный метод** | 100+ строк, комментарии-заголовки внутри | невозможно понять и протестировать | Extract Method |
| **Большой класс** («божественный объект») | `OrderManager` на 3000 строк | любая правка задевает всё | Extract Class |
| **Дублирование** | одно правило в трёх местах | исправил в двух, забыл в третьем | Extract Method, вынос в общий класс |
| **Длинный список параметров** | `create(a, b, c, d, e, f, g)` | путают порядок | Introduce Parameter Object |
| **Одержимость примитивами** | `String email`, `long amountCents`, `String currency` | валидация размазана, легко перепутать | Value Object: `Email`, `Money` |
| **Стрельба дробью** | одна фича = правки в десяти классах | забудешь одно место | Move Method, собрать в один модуль |
| **Расходящиеся изменения** | один класс меняют по пяти разным причинам | конфликты, всё ломается | Extract Class по причинам |
| **Завистливая функция** | метод больше работает с чужим объектом, чем со своим | логика не там, где данные | Move Method |
| **Цепочки вызовов** | `a.getB().getC().getD()` | знание о чужом устройстве | Hide Delegate |
| **Switch по типу** | `switch (shape.type)` в нескольких местах | новый тип — правка всех switch | полиморфизм или sealed + pattern matching |
| **Мёртвый код** | закомментированные блоки, неиспользуемые методы | шум, ложные следы | удалить: история есть в Git |
| **Комментарий вместо кода** | `// проверяем, что пользователь взрослый` над условием | комментарий устаревает | метод с говорящим именем |

## Одержимость примитивами — самый недооценённый

```java
void transfer(String fromIban, String toIban, long amount, String currency) { ... }
transfer(to, from, 100, "KZT");     // перепутал местами — компилятор доволен
```

Когда строка — это IBAN, а `long` — деньги, тип ничего не знает о правилах. Value Object собирает и данные, и правила:

```java
record Iban(String value) {
    Iban { if (!IbanValidator.isValid(value)) throw new IllegalArgumentException("bad IBAN"); }
}
record Money(BigDecimal amount, Currency currency) { ... }

void transfer(Iban from, Iban to, Money amount) { ... }   // перепутать типы нельзя
```

Невалидный IBAN теперь нельзя даже создать — проверка в одном месте, а не в каждом сервисе.

## Как рефакторить безопасно

Рефакторинг по Фаулеру — это **изменение структуры без изменения поведения**, маленькими шагами. Не «перепишу этот модуль за выходные».

1. **Сначала тесты.** Нет тестов на этот кусок — напиши характеризующие тесты: зафиксируй текущее поведение, даже странное.
2. **Маленький шаг.** Одно переименование, один вынос метода.
3. **Прогони тесты.** Зелёные — коммит.
4. **Повтори.**

IDE умеет большинство рефакторингов автоматически и безопасно: Rename, Extract Method/Variable/Class, Inline, Move, Change Signature. Пользуйся ими, а не правкой руками.

<Takeaways>
- **Запах** — не баг, а признак будущей боли. Каталог — «Рефакторинг» Фаулера (1999).
- Частые: длинный метод, большой класс, дублирование, длинные параметры, **одержимость примитивами**, стрельба дробью, switch по типу, мёртвый код.
- **Value Objects** (`Money`, `Iban`) делают невалидное состояние невозможным.
- Рефакторинг — **без изменения поведения, маленькими шагами, под тестами**, инструментами IDE.
- Switch по типу → полиморфизм или **sealed + pattern matching** с проверкой полноты компилятором.
</Takeaways>
