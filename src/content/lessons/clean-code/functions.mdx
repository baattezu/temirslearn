Функция — основная единица, в которой мы думаем о коде. Хорошую функцию можно понять, не заглядывая внутрь вызываемых ею функций, и можно вызвать, не боясь сюрпризов. Ниже — несколько правил, которые к этому ведут, и честно о том, где их перегибают.

## Одна задача на одном уровне абстракции

Самая частая проблема — функция, в которой смешаны разные уровни: бизнес-решение, работа со строками и SQL в соседних строках. Читатель вынужден постоянно переключаться между «что мы делаем» и «как именно».

<Compare

    if (email == null || !email.contains("@") || email.length() > 254)

## Аргументы

- **0–2 аргумента** — легко. **3** — терпимо. **Больше** — скорее всего, они просятся в объект.
- **Флаговые аргументы** (`render(true)`) — функция делает две разные вещи. Что значит `true` при чтении вызова — неизвестно.
- **Выходные аргументы** (функция меняет переданный список) удивляют. Возвращай результат.

## Никаких сюрпризов: разделяй команды и запросы

Бертран Мейер сформулировал **Command–Query Separation**: метод либо **отвечает на вопрос** (возвращает значение, ничего не меняя), либо **выполняет команду** (меняет состояние, ничего не возвращая). Не то и другое сразу.

```java
// сюрприз: «проверка» тихо создаёт сессию
public boolean checkPassword(String user, String pass) {
    if (hasher.matches(pass, storedHash(user))) {
        sessions.start(user);     // побочный эффект, о котором имя молчит
        return true;
    }
    return false;
}
```

Кто-то вызовет `checkPassword` в форме смены пароля — и получит лишнюю сессию. Побочный эффект должен быть виден в имени или вынесен отдельно.

## Размер: насколько короткой должна быть функция

«Чистый код» предлагает функции по 4–6 строк. На практике это часто перебор: логику размазывают по десяти крошечным методам, и чтобы понять одну операцию, приходится прыгать по файлу. Джон Остерхаут в «Философии проектирования ПО» спорит с этим: важнее **глубина** — простой интерфейс, за которым скрыта существенная работа, — чем малый размер.

Разумное правило: функция помещается на экран, делает одно дело на одном уровне абстракции, и её имя полностью описывает, что она делает. Если выносимый кусок нельзя хорошо назвать — может, его и не надо выносить.

<Takeaways>
- **Одна задача на одном уровне абстракции**: описывается одним предложением без «и».
- **Мало аргументов**; флаги — признак двух функций; результат возвращай, а не пиши в аргумент.
- **Command–Query Separation**: либо вопрос, либо команда. Побочные эффекты — видны в имени.
- **Сторожевые условия** вместо пирамиды вложенности.
- Размер — не самоцель: важна понятность и «глубина», а не 4 строки любой ценой.
</Takeaways>
